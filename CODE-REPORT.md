# CODE-REPORT — A Developer & Founder Guide to Phoenix-Extended + the Attack Harness

*Read this top-to-bottom. The first two sections are for anyone (including a non-technical
founder); the rest goes progressively deeper for a developer onboarding to the codebase.
Everything here is synthesized from the actual source under `build/`, not from the phase
reports.*

---

## 0. The one-paragraph version

This repository contains two things that work together. **Extended Phoenix** is a
Kubernetes "operator" (a background controller) that defends AI/inference workloads using
**Adaptive Moving Target Defense (AMTD)** — the idea that a target you keep *moving*
(rotating pods, rebuilding them from a known-good image, relocating them to a clean
machine) is much harder to attack than a static one. The **Attack Harness** is a
benchmark that plays the role of a red team: it launches realistic attacks at a cluster
*you own* and measures, with hard numbers, whether a given defense actually disrupted each
attack. Phoenix is one of the defenses the harness can test. Together they answer the
question a founder cares about: *"what does this product actually stop, and is it worth the
cost?"*

---

## 1. Overview: the two systems and how they relate

### Extended Phoenix (`build/phoenix-extended/`)
A Kubernetes operator. You give it a policy (a custom resource called an
`AdaptiveMovingTargetDefense`, or **AMTD**) that says *"for these pods, when this kind of
security event happens, take this defensive action."* Phoenix watches the cluster and,
when a matching event arrives, **mutates the moving target** — most often by rotating the
pod (deleting and recreating it, optionally from a fresh image with a hardened config),
but also by swapping to a pre-warmed replacement, restoring it from a signed golden image,
or relocating it to a clean node. It is **reactive and policy-driven**: it does not invent
attacks to respond to; it acts when an external sensor (Falco, Prometheus, KubeArmor, or a
timer) reports something, and only if your policy says to.

"Extended" means: this is the upstream R6 Security Phoenix operator **plus** the AI/inference
capabilities described in R6's papers and product pages that were not in the open code —
built out faithfully across eight phases. The original repos under `repos/` are untouched;
all new work lives in `build/`.

### The Attack Harness (`build/test-harness/`)
A Go program that is a **plugin-based attack/benchmark lab**. It runs a matrix of
*attack scenarios* × *defender arms* × *trials* against an owned cluster and emits a single
comparable metric schema. Each **scenario** is a realistic attack with a concrete
"did-it-succeed" oracle; each **defender arm** is a defense strategy (including the real
Phoenix operator). The harness is how we *measure* Phoenix rather than assert it.

### How they relate
The harness has a defender arm called **`d-fullphoenix`** that **builds and runs the real
extended-Phoenix operator**, installs its CRDs, applies an AMTD policy, and — where a
scenario calls for it — injects the security event that drives a Phoenix action. So the
harness is the lens through which we see what Phoenix genuinely disrupts, compared against
"no defense," a "blind timer," and "random rotation at the same rate." A future product,
**Phorvex**, will drop in as just another defender arm with zero harness changes.

## 3. Extended Phoenix, explained

### 3.1 The core idea (how a defense actually fires)
Everything routes through one reactive pipeline:

1. An external **sensor** (Falco/Prometheus/KubeArmor) or the **time-based trigger** notices
   something and creates a **`SecurityEvent`** custom resource. A SecurityEvent carries a
   `Rule{Type, ThreatLevel, Source}` (e.g. `{panic, high, FalcoIntegrator}`), optional
   `AnomalyScore`/`Metrics`, and the `Targets` it concerns.
2. The **`securityevent_controller`** looks at every `AdaptiveMovingTargetDefense` (AMTD)
   policy. Each AMTD has a `Strategy[]` list of `{Rule -> AMTDAction}` entries.
3. The **matcher** decides which strategy entry the event matches.
4. The matched **action** is executed on the pods selected by the AMTD's `PodSelector`.

This is the **design rule that makes the system clean**: *every* defensive capability is
reachable only through this public interface — an AMTD `Strategy[]` entry triggered by a
SecurityEvent. There are no side doors. That is why the harness can exercise any capability
just by emitting the right event.

### 3.2 The six CRDs (the system's vocabulary)
| CRD | Scope | What it is |
|---|---|---|
| **AdaptiveMovingTargetDefense** (AMTD) | namespaced | The policy: which pods to protect (`PodSelector`), the `Strategy[]` of rule→action mappings, the matcher mode, the rotation/scoring/trust knobs. |
| **SecurityEvent** | cluster | The trigger: a normalized "something happened" record (`Type/ThreatLevel/Source` + optional score/metrics + targets). The only thing that makes Phoenix act. |
| **WarmInferenceSet** (`wis`) | namespaced | A warm pool of pre-loaded replica pods behind a leader Service, for near-instant cutover (the warm-swap control plane). |
| **WorkloadBaseline** (`wb`) | cluster | The signed "golden" reference (image digests + signature policy) a workload should match; drift against it triggers a restore. |
| **NodeRotation** (`nrot`) | cluster | A request to cordon/drain a node and relocate its workloads to a clean node (the node-level move). |
| **ContextMutationPolicy** (`cmp`) | namespaced | A reusable "mutation recipe" (image/env/GPU overlay) that a rotation applies — e.g. swap to a hardened image and drop GPU on panic. |

### 3.3 The actions (`AMTDAction`, a one-of union)
An `AMTDAction` sets exactly one field (`MaxProperties=1`). Five are inherited from
upstream R6; four are the new AI/inference capabilities.

**Inherited (upstream R6):**
- **Disable** — scale/stop the workload.
- **Delete** — evict the pod (its owner recreates it). This is the simplest reactive move.
- **Quarantine** — isolate the pod (network/policy) for forensics.
- **Debugger** — attach a debug context.
- **CustomAction** — an escape hatch with overridden ports.

**New (the extended AI/inference capabilities), each mapped to its source feature:**
- **Rotate** — *mutating rotation.* Deletes-and-recreates the target, optionally applying a
  `ContextMutationPolicy` overlay (new image digest, env patch, GPU-limit change). This is the
  workhorse: it implements **container/NIM rotation and jittered scheduled rotation** from
  the ADA paper ("regularly destroying/respawning") and the product's "continuous rotation /
  dwell-time collapse." Its durability is the **mutation-survival** design decision: for a
  Deployment/StatefulSet/DaemonSet it patches the *owner template* (so every replica and all
  future replicas inherit the change); for a bare Pod/Job it cold-reschedules and records the
  mutation as non-durable. Guarded by the **storm-guard** decision (idempotence lock,
  minimum-interval floor, readiness checks, crash-loop backoff, max-concurrent rotations).
- **WarmSwap** — *leader→warm-shadow cutover.* Flips a Service's leader label from the active
  pod to a pre-warmed replica in a `WarmInferenceSet`, draining and retiring the old one.
  Implements the product's **warm-swap / "400s→15s" cutover**. Important nuance (the
  "endpoint" design decision): the **external** Service name stays stable; only the
  **backend** pod rotates — so a client holding the endpoint is not invalidated, only what's
  behind it changes.
- **Regenerate** — *restore-from-signed-baseline.* When a workload drifts from its
  `WorkloadBaseline`, verify the golden image's signature (ECDSA/ed25519 over the digest) and
  recreate the workload from it. Implements the ADA paper's **signed/immutable baselines /
  self-healing**. Carries an honest caveat: **signing proves provenance, not benignity** (a
  signed-but-malicious golden would still restore malicious state).
- **NodeRotate** — *panic-move to a clean node.* Cordons/taints/drains the source node
  (honoring PodDisruptionBudgets via the Eviction API) and relocates the workload to a node
  from a clean pool. Implements **node-level MTD**. Gated by the **node-rotate trust gate**
  decision: the triggering event's `Source` must be on an allowlist, its `ThreatLevel` must
  meet a floor, and a destructive `Delete` drain needs human approval — so a forged event
  cannot weaponize node eviction into a cluster-wide denial of service.

### 3.4 The matcher (exact + scored)
`api/v1beta1/matcher.go`'s `MatchStrategy` decides if a strategy rule selects an event. It
has two modes, controlled per-AMTD by `MatcherMode` (**default: Exact**):
- **Exact** (the safe default): compares the three strings `{Type, ThreatLevel, Source}`.
  This is **byte-for-byte identical** to the upstream behavior, so existing policies behave
  exactly as before — the central compatibility guarantee.
- **Scored** (opt-in): adds match expressions over `anomalyScore` and `metrics.<k>` (e.g.
  *"fire if anomalyScore ≥ 0.85"*), with a **rank-aware** `threatLevel` comparison (so
  `threatLevel >= high` correctly matches `critical`). Scored clauses are *inert* under Exact
  mode, so turning them on is always a deliberate opt-in.

### 3.5 The scoring layer (telemetry-driven adaptation)
`scoring.go`/`scoring_update.go` implement the ADA paper's **telemetry-driven adaptation**.
The default is **Passthrough** — it consumes whatever `AnomalyScore` an integrator wrote and
invents no math (a `WeightedScorer` exists but is inert unless you set weights). On top it
applies an **EWMA** (exponentially-weighted moving average, default α=0.3) and **panic
hysteresis** (only declare "panic" after the smoothed score stays high for N consecutive
samples), which drives a shorter computed rotation interval as risk rises and a panic
eviction at the top. This prevents a single noisy spike from triggering a storm.

### 3.6 The trigger paths (who creates SecurityEvents)
- **Timed** (`{timed, info, TimeBasedTrigger}`) → scheduled Rotate/WarmSwap on a jittered
  cadence. The "clock."
- **Drift** (`{drift, …, FalcoIntegrator}`) → Regenerate from the signed baseline.
- **Panic** (`{panic, high, …}`) → Delete/Quarantine/NodeRotate (the urgent path).
- **Policy-violation** (`{policy-violation, high, KubeArmorIntegrator}`) → eviction.
- **Prometheus anomaly** (carries `AnomalyScore`/`metrics`) → the scored path.
- **GatekeeperViolation** → a *receiver* path exists for ContextMutationPolicy, but **no
  upstream emitter produces it** — see §4.

The integrators (Phase-7 normalization) translate native alerts into these canonical
`Type`/`ThreatLevel` strings; without that normalization the string rules would be inert.

## 4. Status per capability (honest)

Classification: **BUILT** = works on CPU/kind; **GPU-PENDING** = built but the headline
number needs real GPU/LLM; **RECEIVER-ONLY** = the action fires if an event arrives but no
sensor emits that event; **ABSENT** = not implemented. (Full evidence in
`build/AI-MTD-AUDIT.md`.)

| Capability | Status | Note |
|---|---|---|
| Inference/NIM rotation (Rotate) | **BUILT** | image/env/GPU mutation, durable owner-template patch |
| Warm-swap control plane (WarmSwap) | **BUILT** | cutover works on CPU… |
| …warm-swap downtime SLO (400s→15s) | **GPU-PENDING** | needs real GPU + model load to measure |
| Endpoint/selector rotation | **BUILT** | backend-only; external Service name stays stable |
| Regenerate (signed-baseline drift→restore) | **BUILT** | signing = provenance, not benignity |
| Node rotation + clean-node selection + trust gate | **BUILT** | …but true cross-node MTTR is **GPU/real-node-PENDING** (kind nodes are kubelet-less containers) |
| Scoring (Passthrough + EWMA + panic hysteresis) | **BUILT** | default Passthrough invents no math |
| Exact matcher (byte-compatible) + scored matcher | **BUILT** | scored is opt-in |
| Integrator normalization (Falco/Prom/KubeArmor) | **BUILT** | emits generic security signals only |
| **GPU-utilization detector** (LLM-jacking trigger) | **RECEIVER-ONLY** | a GPU-*zeroing actuator* exists; nothing *detects* jacking |
| **GatekeeperViolation trigger** | **RECEIVER-ONLY** | CMP receiver wired; no OPA-audit emitter |
| **Model-I/O detector** (Pillar 03 inspector) | **ABSENT** | no hook into the inference pipeline |
| **NeMo Guardrails / semantic prompt filter** | **ABSENT** | R6 explicitly defers this to NeMo |
| **KV-cache isolation** | **ABSENT** | needs real LLM serving |

The practical meaning: Phoenix **neutralizes an attack only where a sensor emits a matching
event**. Where the relevant detector is RECEIVER-ONLY or ABSENT (GPU-jacking, model-I/O,
prompt-injection content), Phoenix can *bound* a foothold by blind rotation but cannot
*detect* the attack — which is exactly what the benchmark measures.

## 5. The attack harness

### 5.1 The plugin architecture
The engine in `internal/core/` knows nothing about any specific attack or defense. It only
knows two interfaces and two registries:

- **`Scenario`** — one attack. Methods: `Metadata()` (name, category, source, the honest
  R6-response tag, MITRE ATT&CK/ATLAS + OWASP IDs, capability requirements), `Setup`,
  `Execute` (the attack kill-chain), `SuccessOracle` (a *concrete observable* check — e.g.
  "a second pod was reached," "N bytes left the namespace," "the stolen token returned HTTP
  200"), and `Teardown`.
- **`Defender`** — one defense arm. Methods: `Metadata`, `Setup`, `Start`, `Stop`,
  `Teardown`. The shipped arms are **`d-nomtd`** (no defense — the positive-control
  baseline), **`d-r6blindtimer`** (blind fixed-interval rotation, no telemetry),
  **`d-randomequal`** (random rotation at the *same mean rate* — the fair comparison),
  **`d-fullphoenix`** (the real operator), and **`d-phorvex-slot`** (a registered stub
  reserved for the future Phorvex arm).
- **Self-registration:** each scenario/defender file has a `func init(){ core.Register…(&X{}) }`.
  The runner enumerates the registries — there is **no central list to edit**.
- **The generic runner** runs `scenario × defender × N trials`, plus a no-attack **negative
  control** (must show ~0 disruption and 0 false defensive moves) and an **adaptive
  attacker** pass (which learns the rotation rhythm and strikes in the lull). Everything is
  seeded from a fixed `masterSeed` for reproducibility.

### 5.2 The metric schema (one struct, every environment)
Every trial emits one `Metric` (in `metric.go`): oracle-achieved, **disruption vs the
undefended baseline**, attacker dwell, time-to-action, security-per-cost, evidence-retention,
plus the additive AI/economics fields — the **split-oracle** result (in-request vs
persistence), the **measured `MTDEffect`** (`NEUTRALIZES`/`BOUNDS-ONLY`/`CANNOT-HELP`,
derived per-arm, never assumed), a **trigger attribution** (so a "missing sensor" is never
misread as a defense failure), and **$ ROI / Schwartau (protection vs detection+reaction) /
attack-reusability**. The same schema is written on kind, EKS, or CoreWeave, so results are
directly comparable; reports + a provenance map (number → command → raw log) are generated
in `internal/report/`.

### 5.3 Recipe: add a new scenario (do not rebuild anything)
1. Create `scenarios/myattack.go`.
2. Implement the five `Scenario` methods. Use the shared mocks in `internal/mocks/` for any
   external/registry/credential/model endpoint — **never touch real ones**. Define a concrete
   observable `SuccessOracle` (and, if the attack has both an in-request and a persistence
   effect, a split oracle). Make `Teardown` idempotent and namespace-sandboxed.
3. Add `func init(){ core.RegisterScenario(&myAttack{}) }`.
4. That's it — the runner, metrics, MITRE coverage, and reports pick it up with **zero core
   changes**. Tag its capability requirements (`CapGPU`/`CapMIG`/`CapMultiNode`) so it
   skip-with-notes where unsupported.

### 5.4 Recipe: add a new defender (e.g. Phorvex)
1. Create `defenders/d_phorvex.go`.
2. Implement the `Defender` methods (stand the defense up in `Setup`/`Start`, tear it down
   idempotently). Reuse `armRotates`/`armIsFullPhoenix`-style helpers if relevant.
3. Add `func init(){ core.RegisterDefender(&phorvex{}) }`.
4. Every scenario now runs against it automatically, and the H1/H2/H3 hypothesis tables fill
   the new arm's column — **zero harness changes**. (The `d-phorvex-slot` stub already proves
   this composes.)

### 5.5 Safety, portability, provenance (the non-negotiables)
- **Containment:** all attack behavior is confined to the configured sandbox namespace by a
  guard that refuses any object elsewhere; category-3 attacks use *mock* cloud/registry/IMDS
  endpoints and CPU-bounded miner stand-ins.
- **Portability:** a per-target config supplies kubeconfig/context/namespace + a **required
  owned/authorized acknowledgement**; the harness verifies the live context *and* apiserver
  host match before any mutation and **refuses any other cluster**. The same plugins run
  unchanged on kind / EKS / CoreWeave / vcluster by config alone.
- **Capability detection:** GPU/MIG/multi-node are detected at runtime; unsupported scenarios
  skip-with-note (never fail).
- **Reproducibility:** every number traces to a command + raw log; everything reproduces from
  the fixed `masterSeed`.

## 6. Build, test, run — and what remains

### Build & test (from each module directory)
```sh
# build/phoenix-extended  (the operator)
go build ./... && go vet ./... && go test ./...     # unit tests; envtest where wired

# build/test-harness  (the benchmark)
go build ./... && go vet ./... && go test ./...
```
Toolchain notes for this environment: there is **no `make` and no `kind` CLI**; CRD
manifests are generated with `controller-gen` via `go run`, and the operator is built to
`bin/manager.exe`. The harness builds to `bin/harness.exe`.

### Run the operator
Build `bin/manager.exe` from `phoenix-extended/cmd`, install the CRDs from
`config/crd/bases` (server-side apply — the schemas are large), apply an AMTD, and run the
manager pointed at your cluster (the harness's `d-fullphoenix` arm does all of this
automatically and pins the operator to the authorized context).

### Run the harness
```sh
# build/test-harness
go run ./cmd/harness -list                      # list registered scenarios + defenders
go run ./cmd/harness -config config.kind.yaml   # run the matrix (smoke: trialsPerArm=2)
#   -config <…bench…> with trialsPerArm>=20      # the full statistical benchmark
#   -resume                                      # accumulate a batch into the same out-dir
#   -dollars-from <metrics.jsonl>                # regenerate the $ view, no cluster
```
Outputs land in the config's `outDir` (`metrics.jsonl`, `report.md`, `report-dollars.md`,
`provenance.json`, `mitre_matrix.md`, `raw/`). Completed runs are preserved under
`out-bench/` (the 18-scenario Kubernetes benchmark, 1,980 trials) and `out-ai-bench/` (the
21-scenario AI benchmark, 2,310 trials).

### What remains
1. **The GPU / real-LLM run.** Six AI scenarios are capability-pending on the CPU-only kind
   cluster (`llm-jacking`, `pillar03`, `co-location`, `gpu-side-channel`, `kvcache`,
   `unbounded-consumption`), and the GPU headline numbers — real LLM-jacking detection,
   warm-swap downtime, panic/node MTTR, KV-cache behavior — are deferred. They run on
   AWS/CoreWeave **by swapping the per-target config — no code change.**
2. **The Phorvex defender arm.** The `d-phorvex-slot` stub reserves the comparison column;
   when the real Phorvex defense exists, it drops in as one file (§5.4) and the existing
   benchmarks fill its results automatically.
3. **The detectors that are RECEIVER-ONLY / ABSENT** (§4) — a GPU-utilization emitter, a
   model-I/O inspector, NeMo semantic filtering — are the honest gaps a future product would
   close; the benchmark already shows exactly where they would change the outcome.
