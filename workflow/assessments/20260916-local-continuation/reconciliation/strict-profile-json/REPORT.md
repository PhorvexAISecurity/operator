# Exact profile JSON key counterexample

On the recorded Tier13 source, both actual operator configuration loaders accept a differently capitalized key after the published key and silently use its value. The independent test writes actual files and invokes LoadMIGProfilesFile and LoadAdapterSourcesFile, with exact-key successful lookup controls first. The intended rejection assertions fail in0.019s with Go1.26.3; no fixture, compile or environment assertion failed.

MIG root `version:0, Version:1` is accepted as version1; a rule with `profile:1g.10gb, Profile:2g.20gb` resolves to2g.20gb. Adapter root version is likewise overwritten, and `source:/models/approved, Source:/models/different` resolves to the latter path. Literal duplicate detection sees different strings while Go typed JSON decoding matches field names without case sensitivity. These are operator-owned configuration interpretation defects, not evidence of tenant privilege escalation, successful hardware action or remote compromise.

Require exactly the published field spelling at every object boundary in both loaders, preserving literal duplicate, trailing input, bounded input, version, namespace/profile/source and duplicate binding checks. Reuse the existing strict serving-security parser pattern where appropriate. Valid canonical files and explicit disabled configuration must retain their behavior. Check root and nested aliases in both key orders, alias-only keys, escaped decoded duplicates, missing fields and canonical positives. No schema migration or new backend capability is required. Recovery-plan parsing is an adjacent source concern, but has not been independently reproduced here and is outside this recorded claim.

Schedule this independent correction with Tier14, using the complete accepted Tier13 as its implementation base. Source semantics are locally decidable; deployed canonical configuration startup compatibility remains a live check. The historical issue register did not cover this concrete parser defect.
