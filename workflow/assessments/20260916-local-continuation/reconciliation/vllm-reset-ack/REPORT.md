# vLLM reset acknowledgement defect — independently reproduced

The production `httpVLLM.ResetPrefixCache` discards the response body and treats HTTP200 or204 as completed reset. The actual loopback request test at `c579aff7ec0507cf5ed64bdc9c82c1aa3a538779` passes an explicit `{"success":true}` positive, but fails all three nonconfirming arms: HTTP200 `{"success":false}`, empty HTTP200 and empty204. The intended RED is0.021s with Go1.26.3. [Probe](lead-baseline-probe.go), [raw result](lead-baseline.log), [source and hashes](baseline.json).

[vLLM0.29 cache API](https://docs.vllm.ai/en/v0.29.0/api/vllm/entrypoints/serve/dev/cache/api_router/) returns a success boolean, including false when reset cannot complete. [The older0.12 API](https://docs.vllm.ai/en/v0.12.0/api/vllm/entrypoints/openai/api_server/) returned an empty200 without checking success. The local fixture reproduces the client interpretation; it does not establish which backend is deployed or measure cache contents.

This is distinct from the M73 pending202 classification and M64 durable dispatch/bookkeeping. M64 controls use an explicitly synchronous service contract; those tests cannot establish real vLLM reset success. Require explicit bounded unambiguous success=true before reset confirmation. A false aggregate result cannot prove zero effect across workers, so retain uncertain dispatch and forbid fallback/retry/epoch or exposure credit. Older unconfirmed endpoints need a real trusted backend acknowledgement contract. Never fabricate a response or silently abort requests to manufacture success. This source fix can proceed independently, with full accepted Tier13 incorporated before final preflight and Native/API verification. Deployed compatibility and availability remain live debt.
