## Historical lessons and unresolved verification

The [22-item ledger](EXISTING-22-VERDICTS.md) mostly records September25 results.
It is valuable history, but its owners, deployment assertions and blockers are
not a current task queue. The new index maps it to current source.

At the previous lead's September28 stop, one vLLM drain run had a joined
brain-driven defense but repeatability was not established; credential testing
had revalidated already-revoked A with legitimate B still working, not a fresh
revocation. An incomplete KV reset had left a protected UNKNOWN operation;
PR408 changed future negative replies, not that historical record. These are
historical observations only. Request the successor's latest evidence before
deciding that any of them still blocks the current deployment.

Static guardrail filtering was often mistaken for proof that the brain had
rotated a guardrail. Raw disclosure versus guarded refusal demonstrates filtering
for that request; a brain-response claim additionally needs the exact decision,
operation and change in behavior. The replacement output case is deliberately
scoped to an owned application output path, not a general jailbreak claim.

Other recurrent failures were missing signal paths, absent profile/RBAC/runtime
installation, requests blocked by an upstream component before the target test,
stale identity bindings, projected-rule propagation delays, incorrect result
polling and unverified network enforcement. Diagnose the first failed stage;
neither math changes nor a new actuator repairs every one of these causes.

Raw historical evidence may exist only on the previous host under
`<git-common-dir>/phorvex-workflow/catalogue-coverage-20260923/`. Legacy references
starting `R/` are private archive pointers, not portable relative links. Obtain
an approved redacted export if that evidence is needed; if unavailable, retain
the historical claim's limitation and execute a new authorized trial. Never
reconstruct a passing raw receipt from a report.

## First session for the successor

1. Reconcile current main and any active colleague branches; agree one owner
   for each live target and shared dependency. Run `python3 workflow/tools/workflow.py doctor`
   once; distinguish historical warnings from actual current blockers.
2. Refresh deployment, workload, policy and profile inventory read-only. Compare
   current live compatibility/arming reasons with the implementation map.
3. Choose one existing case and copy the [case template](CASE-TEMPLATE.yaml)
   into a new campaign round. Define behavior, input mode, acceptable defenses,
   controls and bounds before running it. Use the current application's real
   route and synthetic owned data.
4. Close that case end-to-end and after a repeat/rollout; file and repair the
   earliest demonstrated failure. If an enforcement capability is missing, build
   the scoped actuator as part of that slice.
5. Continue in small batches with independent review and nonconflicting live
   reservations. Then expand from the refreshed workload/trust-boundary matrix.
   Keep controls from the original 22 rather than converting every useful control
   into an artificial attack.

Success means a reusable benchmark with traceable, honest results and identified
remaining gaps. It does not mean every attempted attack must earn DEFENDED or
that a finite catalogue proves the entire stack secure.
