### M-149 · Post-T1-A, the `model-theft` stage is unreachable on GPU fleets without DCGM profiling — the leakage gate's only activity input is honest-absent · **MEDIUM** · 🔴 LIVE · `SENSING->BELIEF`
**What:** After T1-A, arm (1) of `aiStageFromView` gates on `SMOccupancy` alone (`killchain/hazard.go:246`). The only permitted source for `SMOccupancy` is `DCGM_FI_PROF_SM_ACTIVE` (`ingest/prometheus.go:91-100` — an deliberate honesty rule: GPU duty-cycle is never substituted). GPUs without DCP profiling (our T4s) export **zero** such series — measured live: `DCGM_FI_PROF_SM_ACTIVE: 0 series`, so `SMOccupancy ≡ 0` with `SMSource == ""` and arm (1) can never fire. The fix trades a permanently-true gate for a permanently-false one on the shipped hardware: correct (residency is not theft), but the fleet loses all model-theft stage coverage, and the post-deploy "zero-event model-theft: N → 0" diff passes *vacuously* — it must never be cited as evidence the gate discriminates. There is also no metric or status surface that would tell an operator the stage is dark for hardware reasons.
**Fix (not built by T1-A, by design):** an activity fallback with the required physical meaning on non-DCP hardware (e.g. per-pod VRAM *delta* from own baseline, the ticket's option b), and an operator-visible "stage dark: no activity signal" surface. Do not weaken the `prometheus.go` honesty rule to reach for duty-cycle.
