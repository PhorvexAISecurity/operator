### M-22 · `maxMovesPerTick: 0` silently becomes 3 · **MAJOR** · 🔴 LIVE · `CONTROL`
**What:** `EffectiveMaxMovesPerTick` returns the default (3) for an explicit 0 — the opposite of its own comment ("0 is a legitimate decide+log-only budget"). The CRD permits `minimum: 0`. The one numeric availability brake fails OPEN. (Negative values pass through verbatim.)
**Live proof (second pass, 2026-08-21 — two attempts, one decisive):** a first test on a recycled tenant saw zero selections and was (wrongly, for an hour) recorded as "not reproduced on the deployed build." A decisive re-test on a FRESH tenant (`pxv0`, λ at its 0.3 seed, one idle pod, `mode: dryRun`, `maxMovesPerTick: 0`) produced **11 `selected: true` decisions in 8 minutes** — the zero budget is overridden exactly as the code says. The first null was a λ-suppression artifact: on the recycled tenant the dual-descent λ had climbed past the per-$ of fresh pods, masking the budget bug. Lesson recorded in §12: a null live result is only meaningful when selection pressure is independently confirmed. The defective function body is byte-identical at `880d2e4` and `v0.4.39`.
**Status at v0.4.50 (live-campaign re-screen, 2026-08-25):** PERSISTS, and got worse in one specific way. The function was rewritten in the `0.4.43→0.4.50` window (PHVX-115 / PR #70): the comment now reads "preserve an explicit 0 only when the field was deliberately set" — and the body still returns `defaultMaxMovesPerTick` for exactly that case (`if == 0 { return 3 }`). A `+kubebuilder:default=3` marker was added on the field (int, not `*int`), so admission fills unset→3 while an explicit 0 survives to the function, which converts it to 3 anyway. The comment now asserts the fix the code does not contain — the green-but-wrong pattern, in-tree at the deployed build. Consumed via `manager.go:1126` → `coverage.go` `B := pol.MaxMovesPerTick`.
**Fix:** `< 0 → default; else return as-is`, or make the field `*int` — and fix the comment either way.
*Sources: A-3; live-confirmed test V7 (2026-08-21).*
