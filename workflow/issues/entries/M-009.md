### M-9 · `Emitted` is a request-ack, not an effect — the brain never learns what Phoenix did · **MAJOR** · 🔴 LIVE · `ACTUATION->EFFECT`
**What:** No actuator path verifies the cluster actually changed. The Phoenix adapter asserts `Emitted:true` on a successful `SecurityEvent` Create alone; native handlers return after their writes without re-reading; the only effect-observer in the system (`observeReadyRotations`) covers rotate only and, on detecting non-execution, just deletes the pending entry.
**Live proof (corrected 2026-08-21, second pass):** an earlier version of this entry claimed "no Phoenix controller on the cluster; every actuation disappears into a void." **That was wrong** — Phoenix IS deployed, disguised under the generic deployment name `operator-controller-manager` (image `phoenix-amtd-operator`), and it DOES consume the brain's events: Phoenix's own log shows `SecurityEvent was sucessfully applied to the pod` → `Pod: "victim-1" was sucessfully deleted with ACTION: delete`. The full brain→event→Phoenix→delete pipeline works for `rotate`.
**What remains true (and live-confirmed):** the brain gets **zero execution feedback** — its log contains only `decision`/`tick` lines; no status, metric, or audit record reflects whether Phoenix acted, errored, or silently dropped the event. The brain cannot tell success from failure, so nothing downstream (exposure clocks, failure feedback, narratives) can be trusted to reflect reality. Two live-observed consequences: (a) an **adoption race** — events fired before Phoenix's AMTD controller has adopted the target pods are rejected (`Pod "victim-1" is a SecurityEvent target but not AMTD managed`) and lost, so the first actuations after policy creation silently vanish; (b) Phoenix's per-action repertoire is unknown to the brain — it demonstrably executes `rotate` as a pod delete; what it does with AI-specific event types (`phorvex.adapter-rotate`, `phorvex.guardrail-rotate`, …) is unverified, and the M-2 CRD regression currently blocks creating the policies that would test them.
**Fix:** an effect-confirmation seam per actuator (pod UID change for rotate, NP existence for quarantine, cache-miss probe for kv-reset, adapter-list re-read for adapter-rotate); a Phoenix→brain execution-status writeback (or the brain watches `amtd.r6security.com/applied-sec-events` on the pod, which Phoenix already maintains); emit `phorvex.actuation-unconfirmed` audit records; extend pending-observation beyond rotate; document and test Phoenix's per-action repertoire.
*Sources: A-24, A-3(prior audit), R-campaign fossils; corrected by second-pass live test V2 (2026-08-21).*
