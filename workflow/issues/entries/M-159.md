### M-159 · CI never runs the Go unit-test suite — every `go test` guard the fix program lands is local-only; a broken test package ships green · **HIGH** · 🔴 LIVE · `OPERABILITY`
**What:** The only workflow (`.github/workflows/ci.yml`) has no `go test` / `go vet` step in any job (`changes`, `chart-sync`, `build-operator`, `build-console`, `build-phoenix`, `e2e`, `e2e-main`, `deploy` — verified by reading every job), and the operator image build (`deploy/docker/operator.Dockerfile`) runs `go mod download` + `pendingcheck` + compile only — no test stage. The Python E2E suite (`End-to-End/`) is the sole test execution in CI, and it exercises deployed behavior, not unit guards. Consequence: every unit-test guard the fix program adds (T1-D's `phase_vocabulary_test`, T1-E's `verbs_test`/`gate_test`, the RED suites) fires only on the implementer's machine; **main can be CI-green with a test package that doesn't even compile** — which is exactly the standing state: M-157 (`recon/nonfinite_guard_test.go` broken by the M-104 field rename) has been invisible to CI since it landed. It also silently undercuts L3 plans that cite "CI's green run of the completeness test as positive control" (T1-D's L3 plan did — no such run exists).
**Fix (DEVOPS, one job):** add a `unit-test` job to `ci.yml` (`go build ./... && go test ./...` in `phorvex/`, fail the merge on red) — cheap, runner-local, no cluster needed. Until it lands, treat "tests green" claims as machine-local evidence, and require the captured run output in the ticket's evidence dir (the program already does this).
*Sources: K3, 2026-09-06, T1-D L3 (read of ci.yml + operator.Dockerfile at merge `2bed1af`; M-157 as the standing in-tree proof).*
