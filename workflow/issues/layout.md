## Phorvex in 60 seconds

Phorvex is a Kubernetes operator that reacts to security signals by **moving the workload out from under the attacker** (moving-target defense). Each tick it: ingests the cluster graph + `SecurityEvent` CRs → forms a belief about each pod's compromise state (kill-chain stage, P(hold)) → mints weighted "facts" about what an attacker has learned → runs a coverage optimizer that picks the **cheapest actuator that invalidates the most attacker value** under feasibility laws and an SLO cost gate → enacts via one of three actuator backends (Phoenix CRD adapter, native K8s handlers, or hybrid) → writes audit/status/metrics.

The 16-action actuator vocabulary: `rotate`, `quarantine`, `identity-rotate`, `route-rotate`, `debugger`, `custom-inject`, `disable`, `warm-swap`, `mig-rebind`, `kv-reset`, `endpoint-rotate`, `model-shard-replace`, `adapter-rotate`, `request-drain`, `guardrail-rotate`, `kv-migrate-invalidate`.

**What is proven working end-to-end on the live cluster:** `rotate`, `kv-reset` (measured cache flush), `endpoint-rotate` (Service restitch), `adapter-rotate` (LoRA unload, detector-driven closed loop), the kill-switch, and detector→brain→actuator closed loops for two attack classes.

## §15. How the tiering works

A tier is a **barrier**: finish everything in tier *n* before starting tier *n+1*. Within a tier, order by severity and work in any order — items inside a tier do not block each other.

**Two different things create a barrier, and the distinction matters:**

| Barrier | Meaning |
|---|---|
| **hard** | The later fix is *impossible* until the earlier one lands. Four such edges exist, all demonstrated. |
| **verification** | The later fix is possible but **cannot be confirmed to have worked**. Every brain-side fix is verified by diffing decision records, and the record does not currently carry the decision's inputs. |

The verification barrier is the one that puts tier 0 where it is. It is not a technical impossibility — it is that shipping tiers 1–3 without it means changing a system you cannot measure.

**The parallel track is not tier 4.** Those 108 issues have no dependency in either direction that we have established. They can start today, alongside any tier, and they are the majority of the register. We have not established that the 102 have no relationships; we have established that we have no evidence of any. Inventing an order for them would look authoritative and be false. If evidence for a dependency appears, the item moves into a numbered tier.

`M-2/R-3` is in tier 0 because four actuators cannot be switched on at all until the CRD enum admits them, so they cannot be tested in any later tier. `M-144` is in tier 0 because λ pinned at zero means no change to selection can be observed — it is the register entry that `B-1/A-1` resolves.

`M-140` and `M-145` are **not** tier 0. T0's exit criterion can be met on a fresh tenant name (`nats` is the live single-policy case; V7 already established the protocol). Name-keyed state contaminates *which dual you think you are measuring*; it does not stop you writing inputs into the record or un-pinning λ. They sit in tier 1: they change what a "tenant" is as an input. `M-22` is a **companion**, not a member: the natural test lever for un-pinning λ (`maxMovesPerTick: 0`) is dishonest, but T0 can still exit on budget=1 with binding demand.

RECORD-tagged parallel items are natural companions to tier 0's `B-5/R-2/R-9`: same files, and cheapest to land in the same pass even though none of them blocks it.

The old Wave 0–6 demo-unblock list (the previous Priority roadmap) is superseded by this tiering.
