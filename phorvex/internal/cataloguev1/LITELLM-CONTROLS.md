# Installed LiteLLM controls

The two disabled-by-default catalogue profiles observe the exact `litellm` serving Pods separately. `catalogue-litellm-route-health` sends one fixed GET `/health/liveliness` to each Pod's own loopback listener. `catalogue-litellm-credential-boundary` sends that positive control plus GET `/v1/models` with no bearer and with a newly generated, synthetic `sk-catalogue-…` bearer. Each run requires the reviewed two-Pod Deployment, ReplicaSet owners, Service and EndpointSlice target UIDs and addresses, container IDs, installed image digests, mounted ConfigMap digest, and installed route/auth source hashes. These authorities are captured before and after each application GET. A changed pin makes the run inconclusive.

The application GET is performed through one authenticated Kubernetes Pod exec into the exact container, where a fixed Python standard-library script opens one `127.0.0.1:4000` connection. The Kubernetes credential is used only for exec. The script does not read or export the master key or provider key. It generates the invalid bearer in process memory, makes one GET without redirects or retries, reads at most 4097 response bytes, and emits only bounded status, content type, byte count, SHA-256, and a whitelisted error reason. Every request has a five-second deadline and is preceded by a journal intent. There are at most two application GETs for the health profile and six for the credential profile. No inference, provider request, key mutation, customer data, or SecurityEvent is part of either control.

The reviewed installed images are LiteLLM 1.95.0 (`sha256:af8068…d688af`) and 1.98.0 (`sha256:20b504…80ddaf`). The fixed config digest is `14ebebce3b18a492a7aadb5c011bfcd71d8d16d8e8745e305b4f2336664daafb`. Both installed versions define unauthenticated liveness and an authenticated GET `/v1/models` with `user_api_key_auth`; the route and auth file hashes are pinned in the Go source. The admitted six-GET record observed liveness 200 and missing-bearer 401 on both Pods. Its invalid-bearer response was 400, later classified by a separate diagnostic as `NO_CONNECTED_DB`. The permanent credential profile reports that branch as `UNKNOWN_CONFIGURATION_LIMITED`, never as a verified key denial or bypass. A 200 liveness proves only the listener response and does not establish authenticated model serving or model availability.

The profiles are direct functional and configuration observations. Their result explicitly marks brain, actuator, installed defense, and security outcome `NOT_EVALUATED`, with event mode `none`. A normal SecurityEvent is neither required nor expected. The fixed profile ID is the only browser supplied selector; route, target, config digest, namespace, and request shape come from deployment-owned settings.
