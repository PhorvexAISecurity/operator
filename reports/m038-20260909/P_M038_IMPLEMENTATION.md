# PHORVEXSEC-231 / M-38 selector-safe quarantine

Source base: PR135 / 493288eb814377affdac87d6afc222e08d6cc256. This companion PR uses its authoritative boundary reader and request target UID plumbing. Merge PR135 first. This is an implementation dependency discovered in source, not a numbered-tier or Math gate.

## Baseline fidelity
Task169 already expanded beyond ReplicaSet. Current defects were independent Service checks being skipped when an owner selector was found, arbitrary owner semantics/UIDs not validated, swallowed read failures, incomplete negative-expression handling, removal of all owner references, and wholesale rollback overwriting concurrent metadata. These are static/current-source findings, not new live cluster claims.

## Supported behavior
The direct reader gets the Pod and resolves exactly the controller owner, with matching API version and UID. Supported namespaced selectors: apps/v1 ReplicaSet, StatefulSet, DaemonSet, and batch/v1 Job. Bare pods are supported. Unknown owner kinds, missing/mismatched owners, unreadable inputs and empty selectors refuse before writes. Non-controller references are preserved. No wildcard/custom-controller RBAC is added.

All selector-based Services in the namespace are independently checked. Deterministic edits handle matchLabels and In/Exists/NotIn/DoesNotExist, preserve the quarantine marker/epoch and unrelated labels, and validate complete predicates on the final labels. A plan that still matches its owner or any observed selector-based Service is refused, including unintended new membership. Long values receive valid bounded replacements. This is conservative planning, not a minimum edit optimizer. Selectorless Services and manual EndpointSlices remain explicitly unverified, not silently edited.

Plan validation precedes NetworkPolicy creation. Existing same-name policies must match the target UID selector and ingress/egress deny spec. Pod update carries fresh UID/resourceVersion and is not blindly retried. A conflict after policy creation retains the policy and a partial result, including touched objects and failure note, through native dispatch and runner audit fields. Dispatch stays error and Actuated stays false. The policy may not yet select the unchanged Pod, so this partial result is not an isolation claim.

Success acknowledges metadata writes against observed selectors only. It does not prove endpoint convergence, CNI enforcement, stopped existing traffic, replacement readiness, persistent controller detachment or attacker capability invalidation. Other NetworkPolicies may allow traffic because Kubernetes policy semantics are additive. No coverage formula or network grant is changed here.

## Recovery
Version-2 snapshot in the existing Pod annotation stores UID, only changed label baselines/applied values, original/applied owner refs and policy UID. Retry does not overwrite it and verifies existing applied metadata/policy. Explicit NativeActuator.Rollback requires the UID-bound reference, refuses conflicting edits, validates original controller identity, preserves unrelated new metadata and uses conditional policy deletion. Legacy/unverified snapshots require manual inspection rather than destructive wholesale restoration. A failed final cleanup explicitly reports that Pod restoration succeeded but policy cleanup failed.

The annotation is durable with the Pod and validated structurally/against identities, not cryptographically protected. The security/deployment review must verify who can mutate protected Pod metadata. Arbitrary writers able to forge this annotation are outside the verified recovery trust boundary. The implementation does not assert a new protected-storage guarantee or automatically restore/re-admit pods. Multi-object owner/Service/policy reads are not atomic with the Pod write, so subsequent controller changes can invalidate the observed plan.
