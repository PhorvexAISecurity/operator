# Fixed Mongo synthetic-document exposure control

`mongo-exposure-baseline` is a default-off named suite for `c2-mongo-uncredentialed-service-exposure`. It measures one nonce-owned document created through an exact Mongo Pod forward, a separate client Pod's no-credential read through the installed `document-store/mongo:27017` Service, legitimate exact-ID reads before and after, manager-audit coverage, and exact cleanup. It injects no SecurityEvent, requests no actuator, and yields no defense efficacy score. An HTTP/API view must not describe Mongo code-13 denial as a defended result: this first profile has no authorized Mongo credential to establish a positive control after authentication changes.

The server owns `build/test-harness/config.mongo-exposure-baseline.yaml`. Before the profile can be enabled, replace every source placeholder with reviewed DEV pins: logical cluster context and kube-system UID; `document-store/mongo` Deployment, Service and current Mongo image ID; `mongo-defense` policy; singleton manager namespace, Deployment and image ID; and 1–4 allowed Ready untainted CPU Nodes. The producer rechecks current Deployment→ReplicaSet→Ready Pod, Service and owner-bound EndpointSlice, policy UID/generation/spec hash, manager incarnation, and node suitability before mutation. A client on a different eligible node is valid. A scheduler/CNI failure or absent Pod IP is `UNKNOWN` followed by owned UID cleanup, not evidence that Mongo denied the read.

The console image already packages reviewed `config*.yaml` files under `/data/build/test-harness`; the named-suite runner reads the server-owned config there. It replaces the template run ID, nonce and relative output directory with one private absolute run path before harness validation, and permits no browser override of database, collection, document, Pod, Node, target, command, signal or expected action. The fixed client image is pinned in Go; no runtime package download, Secret, ServiceAccount token mount or general Pod executor is part of this profile. Launch and all run/result reads require the configured logical and physical target plus `document-store` tenant grants. A previously unsafe Voice run remains governed by the existing global gate.

The chart adds no Mongo authority by default. `phorvex.console.mongoExposure.enabled=true` renders exactly one Role and binding in the **existing** `document-store` namespace; it requires `phorvex.console.enabled=true` and passes `PHORVEX_CONSOLE_MONGO_EXPOSURE_ENABLED=true` to the console. The backend requires that opt-in flag as well as valid config and current source admission. The added verbs are Pods get/list/create/delete, Pod logs get, Pod port-forward create, fixed Service `mongo` get, and EndpointSlices get/list. It does not create or delete the namespace, write Services or policies, or grant Secret access. Render and inspect the permission delta with `tools/test_mongo_exposure_chart.py` before any deployment. The namespace and all installed source/config pins must already be valid; enabling the Role alone does not establish profile readiness.

The worker writes an intent before each mutation, stores returned collection UUID and client Pod UID, and never retries an ambiguous create. Accepted exposure requires the bounded original mongosh line, its SHA-256, the same collection UUID and owned document across legitimate controls, one exact client read, a contiguous same-generation audit window, and confirmed UUID/UID cleanup with forward closure. The public result shows only typed statuses, exact source/client/policy UIDs, the bounded raw reply hash and size, and up to 64 joined manager decision projections. Raw document/reply bodies remain private. An audit gap, unknown create, mismatched source, or unconfirmed cleanup keeps the finding `UNKNOWN` and the run unsafe to retry until exact-ID reconciliation.

This is a configuration exposure control. It does not test Mongo tenant authorization, customer data, natural detection, or a Phorvex response. A later injected-response scenario needs its own registered claim and independent effect and legitimate-service oracles.
