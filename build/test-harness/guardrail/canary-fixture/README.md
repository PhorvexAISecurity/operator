# Guardrail canary fixture: loopback bridge checkpoint

This is a **tooling component, not a runnable catalogue case or security result**. It lets a future run-owned CPU proxy use the unchanged installed guardrail source, whose upstream is hardcoded to `127.0.0.1:8001`. The bridge listens only on that loopback port in the same fixture Pod and forwards at most three sealed chat requests to one exact raw vLLM Pod IP on port 8001. It never uses the `vllm` Service on port 8000: that route would pass through the existing guardrail and filter twice. The production CLI refuses a loopback raw target; unit tests alone use an explicit internal loopback seam.

The installed source hash required in every manifest is SHA-256 `fba39e68dea763043125b29416b832418387a6780e8cce067cbe0121104d09ce` for the retained `guardrail_proxy.py`. The newer checkout `../guardrail_proxy.py` is different and cannot substitute for an installed-source comparison. A read-only 2026-09-24 10:30 UTC check observed the exact installed raw vLLM Pod answering `/v1/models` on port 8001 through an API proxy, with Pod and container identity stable across the check; the normal Service uses port 8000. This establishes raw-port availability **from that observation path only**, not cross-Pod reachability, loaded-weights closure or an inference result. **No proxy image, dependency closure, classifier weights or in-memory model identity is supplied here.** An eventual image must pin the full byte-identical proxy, Python/dependency image digest and both full model snapshot/file digests, start offline, and attest those exact loaded/runtime inputs. Historical cache revisions and the installed CPU Torch version are evidence leads, not image pins. No image is built or downloaded by this component.

The coordinator, not the bridge, must create a private canonical absolute run directory (`0700`) and fsync `manifest.json` (`0600`) before any request. It supplies its SHA-256 to the bridge out of band and injects `POD_UID` from the Kubernetes downward API. The manifest schema is `phorvex.guardrail-canary-bridge.v1`; its **exact** fields are `schema`, `runNonce` (24 lowercase hex), `runDir` (the exact canonical private directory), `createdAt`, `expiresAt` (UTC Z, at most 600 seconds apart), `proxySourceSHA256`, `fixture`, `target`, `model`, `canarySHA256`, and `requests`. Copying the manifest into a different run directory is refused. `fixture` contains `namespace=vllm`, `podUID`, `proxyContainerID`, `bridgeContainerID`, `proxyImageID`, `bridgeImageID`; `target` contains `namespace=vllm`, `podName`, `podUID`, `podIP`, `containerID`, `imageID`, `port=8001`. `requests` has **exactly** `disclosure`, `say_ok`, `arithmetic` keys, each a distinct full raw-body SHA-256. The coordinator makes the bodies using `request_body(model, private_canary, slot)`, signs off on their fixed system/user turns and keeps the synthetic canary private. The bridge accepts neither browser-supplied text nor a different body with an updated digest if its conversation shape/text changes. It does not log body, canary, user text or headers.

Before each slot, the coordinator fsyncs `attest-<slot>-before.json` with `schema`, `manifestSHA256`, `slot`, `phase=before`, `observedAt`, both exact identity objects and `proxySourceSHA256`, all from fresh authoritative API reads. This must be no older than ten seconds when the bridge receives the request. The bridge checks it and durably appends a unique `INTENT` **before** one network dispatch. It constructs outbound headers itself, accepts only `POST /v1/chat/completions` with `Host: 127.0.0.1:8001`, `Content-Type: application/json`, `X-Canary-Run` and `X-Canary-Slot` matching the sealed manifest, and refuses other/duplicate headers, paths, bodies, methods, redirects and response overflow. One slot is never retried, including after a timeout or ambiguous send. A terminal row is fsynced before the client receives the bounded response. An existing journal refuses process restart/replay.

After the client response, the coordinator makes a **new** authoritative API read and fsyncs `attest-<slot>-after.json` with the same exact keys and `phase=after`. `bridge.py finalize` checks that this read occurred after the terminal record, matches the original fixture and raw target identities, and writes `final-<slot>.json` once. A missing/malformed/drifted attestation cannot yield `ATTESTED_RESPONSE`; an ambiguous dispatch remains `UNKNOWN_AFTER_DISPATCH`. The bridge cannot itself prove that the supplied Kubernetes observations came from the API, that the raw Pod IP is reachable, or that raw HTTP was served by the pinned vLLM process. Those are coordinator admission and independent review requirements. Do not interpret bridge receipts as canary disclosure, benign availability, action effect or defense efficacy.

Production CLI shapes (no network request is made by `validate` or `finalize`):

```text
POD_UID=<downward-api-uid> python3 bridge.py validate --run-dir /private/absolute/run --manifest-sha256 <64-hex>
POD_UID=<downward-api-uid> python3 bridge.py serve --run-dir /private/absolute/run --manifest-sha256 <64-hex>
POD_UID=<downward-api-uid> python3 bridge.py finalize --run-dir /private/absolute/run --manifest-sha256 <64-hex> --slot disclosure
```

Only `serve` binds `127.0.0.1:8001`. It uses standard-library HTTP with a 30-second upstream timeout, a 4-KiB request and 64-KiB response bound, no proxy environment and no automatic retry/redirect. The coordinator must terminate the run at its deadline and treat process/container replacement, target drift, leftover journal or incomplete cleanup as partial. A run-owned Pod/Service/Policy, source-pinned proxy image, exact raw model reachability, protected operation join and independent canary/legitimate response reader remain **unimplemented**. The ordinary shared vLLM serving stack is not changed by these files.

Local tests: `python3 -m unittest -v test_bridge.py`. They use a disposable loopback HTTP backend and do not contact Kubernetes, providers or an installed service.
