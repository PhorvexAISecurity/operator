## As-deployed reality (read before predicting anything)

- **Voice bot** (`voice`): 2 replicas, non-stateful → **rotate feasible**. Policy `voice-defense` enables **`[rotate]` only**, `reactiveOnly`, `minAvailableReplicas: 1`, 5s tick, `antiOverRotationWindow: 90s`.
- **Chroma + Mongo** (data stores): **1 replica each, stateful (PVC)**. Under `minAvailableReplicas ≥ 1`, a foothold here has **rotate infeasible (stateful-integrity) AND quarantine infeasible (availability floor 1−1<1) → None**. Quarantine only becomes feasible at `minAvailableReplicas: 0` (the condition the T6 canary ran under).
- **CRM, MCP** : 1 replica. **litellm/vLLM**: verify replica/stateful at test time; vLLM is 2-rep, `HasGPU`, annotated (`model-id`, `kv-reset-path=/reset_prefix_cache`). No LoRA, no guardrail tier deployed. GPU = T4, **no MIG**.
- **⚠ Test step 0 for ANY non-rotate actuator:** it must be added to the policy's `actions.enabled` (live = `[rotate]`). Every "Expected" below is *what the brain picks once that actuator is enabled*. Selection ≠ effect: **quarantine's NetworkPolicy is unenforced** (`ENABLE_NETWORK_POLICY` unset) until set, so quarantine tests prove *selection* only.
- **⚠ Unwatched-workload caveat (audit 2026-08-10):** locally, only the bot manifest carries `r6th.io/rotation-target=true`, and only `voice-defense` (bot) + `vllm-defense` (vLLM) are known policies. If CRM/MCP/Chroma/Mongo/litellm have **no selecting policy** (verify live: `kubectl get phorvexpolicy -A` + pod labels), Phorvex never even *sees* those pods — rows like Q3 then show "unwatched" (silence), NOT "watched-but-nothing-feasible". To prove the feasibility gap you must first put the store under a policy at `minAvail:1`; *then* "rotate vetoed + quarantine infeasible → None" is the correct prediction.
- **⚠ Second-order artifacts (audit 2026-08-10, from `feasibility/defaults.go`):** (a) `antiOverRotationWindow` gates **every** move (not just rotate) on the pod-identity clock — a pod younger than the window (fresh vLLM replica) has **all** moves infeasible, kv-reset included → after any pod restart, wait > window (voice=90s; check vllm-defense live) before expecting a move. This is also a candidate explanation for T8-anomaly F2 (fresh canary pods categorically infeasible). (b) `maxMovesPerTick:1` serializes multi-pod events (one move per tick). (c) kv-reset keeps the pod alive → does NOT reset the identity clock → it is re-fireable every tick (no 90s re-block).

> **K1 effect-oracle caveat (audit 2026-08-10 — read before running):** on stock vLLM APC, cached KV is a *pure function of the prefix tokens* — a victim request only inherits "poisoned" KV if (a) the poison is in its own prompt tokens (content poisoning — kv-reset does **not** cure it, the KV just gets recomputed identically), or (b) a **block-hash collision** decouples KV from tokens (K3, Borderline), or (c) server-side session KV (not stock vLLM). So the honest effect oracle is: *the attacker's planted cache state is verifiably evicted* (re-run the identical attacker request → goes from prefix-cache HIT to MISS; `vllm:gpu_prefix_cache` usage drops) **without the pod dying** — that is the "surgical beats rotate" proof. Claiming "the injection is cured" only holds under (b)/(c) — do not overclaim. Also verify at test time that `/reset_prefix_cache` is actually exposed on the live vLLM (v0.7.3 since Aug 3 — docs previously said 0.6.6.post1; verified 200 at T12). If 404, that's a pre-flight finding, not a Phorvex failure. **Alternative framing that makes "evict the injection" literally true:** run the voice bot's LLM on the local vLLM and let a poisoned *caller-memory* note (M4) enter the shared system-prefix — the poisoned prefix then caches and serves future callers; kv-reset + memory fix evicts.
