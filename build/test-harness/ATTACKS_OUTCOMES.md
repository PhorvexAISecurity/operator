### T1 · GP1/GP2/R1 — Call-wiretap foothold  🟢 DEFENDED
- **Class:** in-pod foothold (`R6Covers`). Maps to GP1/GP2, voice A5.
- **Setup:** planted a "/tmp wiretap" marker + a detached capture process inside a running `voice-bot` pod.
- **Trigger:** `SecurityEvent{Panic, critical, ExternalDetector}` at the pod (simulated detector).
- **Oracle:** is the wiretap marker still present in any `voice-bot` pod after the response window?
- **Result:** wiretaps alive = **0**.
- **How Phorvex reacted:** rotated the compromised pod; the fresh pod had no marker. Rotation clears ephemeral in-pod state.
- **Note:** the "wiretap" was a stand-in marker, not real audio interception — it validly tests foothold-persistence-vs-rotation, not interception.

### T2 · V10/R2 — API-key theft from pod env  🔴 NOT DEFENDED
- **Class:** static-credential theft (`R6CannotRespond`). Maps to the voice B9–B11 family.
- **Setup:** read the mounted secret env from a `voice-bot` pod; recorded SHA-256 fingerprints of 5 keys (values never printed).
- **Trigger:** `SecurityEvent` → Phorvex rotated the pod.
- **Oracle:** are the stolen key fingerprints still valid on the fresh pod?
- **Result:** **5/5** keys identical after rotation — still valid.
- **How Phorvex reacted:** it **did** rotate the pod (acted correctly) — but the same Secret re-mounts, so the exfiltrated keys never changed. Acted, achieved nothing. Fix = proactive credential rotation (an actuator that doesn't exist yet).

### T3 · V7/N2 — Transcript exfil from Mongo  🔴 NOT DEFENDED

### T6 · GP10/Q2 — stateful workload → quarantine-not-rotate  🟡 PARTIAL (decision right, containment cosmetic)  ← the judgment win
- **Date:** 2026-08-09. **Class:** stateful integrity (`R6Covers`, GP10). Proves Phorvex **contains** a stateful pod instead of **destroying** it — the "don't delete the DB" judgment.
- **Setup:** throwaway `pxtest` namespace, a **2-replica StatefulSet `pgcanary`** with a `volumeClaimTemplate` (per-ordinal PVCs `data-pgcanary-0/1`, gp2-csi EBS), each pod writing persistent `state.db` ("rows=5000 CUSTOMER-PII"). PhorvexPolicy `pxtest-defense` with **both `rotate` AND `quarantine` enabled**, `reactiveOnly: false`, `proactiveFloor: 30s`, `lambda: 0.1`, `minAvailableReplicas: 1`. The `statefulIntegrity` feasibility rule (`feasibility/defaults.go`) makes **`rotate` on a stateful pod infeasible** ("would destroy single-writer/long-running state; prefer quarantine"). So with both actions enabled, the greedy engine falls to `quarantine`.
- **Trigger:** **none** — proactive path (no `SecurityEvent`), same as T5. `hazard≈0.0001–0.008` (nothing detected).
- **Oracle:** does Phorvex choose **quarantine over rotate**, and do the pods stay alive with their state?
- **Result:** ✅ Phorvex **quarantined** on its own timer. ## Findings / anomalies (surfaced during the T8 canary work — for the Phorvex team)

These aren't attack verdicts — they're **Phorvex behaviors** hit while building the T8 rig on a synthetic busybox canary (`pxtest/fcanary`, a 2–3 replica stateless Deployment). Both are reproducible and worth engineering attention.

- **F1 — Quarantine sprawl on ReplicaSet-managed pods (likely a bug).** With `actions.enabled:[rotate,quarantine]`, Phorvex chose **quarantine** on the stateless Deployment pods. The Phoenix quarantine actuator *adopts* each pod under an `AdaptiveMovingTargetDefense` ownerRef (detaching it from the ReplicaSet) → the Deployment spawns a replacement → the replacement gets quarantined next tick → **unbounded growth: reached 55 pods / 54 NetworkPolicies and still climbing** before teardown. (T6's StatefulSet didn't sprawl only because its RWO-PVC replacements were stuck Pending, capping growth.) A deny-all-NP quarantine that adopts pods away from their controller has no termination condition on a replicated workload.
- **F2 — Rotate categorically infeasible on the busybox canary.** Under `actions.enabled:[rotate]` only, every tick logged `selected:0, infeasible:N` for all fcanary pods (2 *and* 3 replicas) — Phorvex **took no action**, even after a critical `SecurityEvent`. So a rotate-specific feasibility rule vetoed rotate for this pod (candidates: mis-classification as stateful, a token/SLO floor that only constrains rotate, or — per the 2026-08-10 audit — **anti-over-rotation on fresh pods**, since it gates ALL moves on the pod-identity clock). **This is a canary artifact, not a general gap** — the real `voice-bot` rotated fine (~9s, T4/T8). But it means synthetic busybox canaries are *not* faithful rotate targets, and it's worth confirming which feasibility rule fires (if a non-LLM CPU service could ever trip it, that would be a real gap).
- **F3 — Quarantine containment is COSMETIC on this cluster (high impact; = T9).** See the T9 entry. `ENABLE_NETWORK_POLICY` unset on `aws-node` → deny-all NPs have zero effect.
- **F4 — The "advanced" actuators are cosmetic relabels (highest-impact finding; = T10 + T11).** identity-rotate and route-rotate are *enabled, selected, and enacted* (real decision-log lines, `feasible:true`, confident `r6Note` marketing copy) — but each only **adds an epoch label to the pod** and does nothing else (see T10/T11 entries). **The consequence is the engagement's central correction:** on this deployment, **pod-rotate (delete) is the *only* actuator that produces a real security effect** — until T12 proved kv-reset (real flush) and T17 proved endpoint-rotate (real route-key re-key + Service restitch, live). *(Fair-framing note: the epoch-label design presumably intends a companion mechanism — a Service that selects on the epoch label, or a token-invalidation step — to consume these labels; none is wired up on this cluster, so the labels are inert.)*
- **F5 — Dynamic-λ sensitivity of the bundle moves (T17 attempt 1).** The served-model bundle facts (`endpointPath`/`inflightRequests`/`guardrailBypass` ≈ 0.73) are minted WITHOUT the scarcity multiplier `s` (`recon/ucw.go:52-56` runs before the bundle append at :80). At elevated dynamic λ (≈3.5, e.g. right after proactive periods) they cannot clear `λ·cost` and the engine selects NOTHING — the "policy-scope + prune rotate" recipe is necessary but not sufficient. Once λ decayed (≈0.8–1.05 under reactiveOnly calm), the same recipes all fired (T14–T17). Selection claims for B1/B2/B3/K4/B5 must state the λ window.
- **F6 — Rotate is conformal-cost-gated on GPU pods (T18/T19).** `CostCeiling = NormSparsity+FlowDisruption+0.2` (1.2 default) vs rotate's GPU cold-load envelope (`CHi ≈ 1.38`; T4 envelope constant 0.2925). Raising the ceiling via weights raises CHi in step — rotate stayed excluded at ceiling 2.1 too. On GPU serving pods the nuke is structurally priced out; only surgical moves pass the gate. (CPU pods unaffected — T4/T8 rotated fine.) If the conformal envelope gets calibrated tighter (real p99 residuals — see ns `phorvex-cost-validate-vllm`), rotate can re-enter; revisit then.
- **F7 — Missing `services` RBAC on the actuator (found by T17, FIXED live).** `endpoint-rotate`'s Service restitch needs `services get/update/patch`; clusterrole `phorvex-actuation` only had pods/ephemeralcontainers/networkpolicies. Patched live 2026-08-10; **gitops follow-up: bake the rule into the deploy manifests** or the next redeploy loses it.
- **F8 — `request-drain` fail-close label wart (T14).** On stack-drain failure the handler restores `phorvex.ai/serving` to the PREVIOUS value — which was absent — and ends up writing an empty-string label instead of deleting it. Cosmetic, but it pollutes label selectors that test for presence.

Net: zero working inference through any credential; the voice bot boots and answers calls but cannot complete an LLM turn. Fix options for DevOps: point `gpt-4o-mini` at the in-cluster vLLM (`model: openai/Qwen/Qwen2.5-7B-Instruct-AWQ`, `api_base: http://vllm.vllm.svc.cluster.local:8000/v1`, dummy key — keeps transcripts in-cluster, free), or set a real `OPENAI_API_KEY` + attach the litellm DB. Add an end-to-end "bot completes one LLM turn" smoke check — this was invisible until probed.
- **F17 — Fresh pods are undefendable for the whole `antiOverRotationWindow` (T45 attempt 1; code-confirmed).** The anti-over-rotation rule (evidence-retention guard) reads the pod-identity exposure clock as "time since last move" — but that clock **seeds from the pod's `StartedAt` on first observation** (`exposure/clock.go:70-78`). So a brand-new pod looks "just moved": every actuator (including surgical ones that don't restart anything) is vetoed until pod-age > window. Observed live: `GuardrailBypass` critical event fired 3m after a rollout → `selected:0, infeasible:1` for the entire watch; the identical re-fire at pod-age 16m selected in 6s. On this rig the window is **15m** (`vllm-defense.budget.antiOverRotationWindow`) — for a slow-booting GPU pod the undefended-*after-Ready* window is `15m − bootTime`. An attacker who times the attack to just after a deploy/scale/rollout gets a guaranteed no-response window. The rule's intent is "don't wipe evidence of OUR last actuation" — pod birth is not a Phorvex actuation. Fix direction: track "last Phorvex move on this pod" explicitly (or seed never-actuated pods as already-outside-the-window), keeping the guard only for post-actuation evidence retention.
- **F18 — warm-swap fights Deployment-managed leaders (T46 restore; code-confirmed, ~9-min churn loop live).** The swap itself was perfect (shadow promoted, old leader drained + retired) — then the old leader's **Deployment** immediately recreated it (the pod template carries `role=leader`). The crash-resume reconciler (`warmswap_resume.go:44-76`) saw two leaders in the swap-group and "converged": `pickSurvivor` prefers a Ready pod, so **every recreated 7B pod was reaped while still booting** (`warm-swap resume: converged wedged swap {reaped:1}` every 10s), the Deployment recreated it again, and the loop ran until an operator manually relabeled the promoted shadow back to `warm-shadow` (ending the double-leader). In the scuffle a Ready-tie can even reap the *shadow* (youngest-wins tie-break, `:102`). Root cause: `warmCutover`/`rewarmShadow` assume Phorvex owns the leader lifecycle (rewarm-to-N), but a Deployment-managed leader is resurrected by its own controller — **two controllers fighting over the same pods**. Fix directions: (a) warm-swap should detect an `ownerReference` on the leader and patch/scale the owning Deployment instead of bare-deleting its pod; (b) the reconciler should skip double-leader convergence when a leader has a Deployment ownerReference (let the workload controller win); (c) `rewarmShadow` cloning a Deployment-owned pod spec creates an unmanaged duplicate — clone into the pool's owner instead. Until then: warm-swap is clean on bare pods / operator-managed pools, and on Deployment-managed leaders it needs the documented restore procedure (relabel the shadow back to `warm-shadow` promptly after the flip — do NOT wait for the recreate to become Ready first, it never will).
- **F19 — Handler forensic Notes are constructed but never persisted (T49; code-confirmed).** Every AI handler returns a rich `HandlerResult.Note` ("local KV invalidated; cross-worker: … deferred sentinel"), but `runner/manager.go:645` only carries `Handler`/`ObjectsTouched`/`RollbackRef`/`MutationKind` into the audit record — **the Note is silently dropped**. Live consequence: the audit decision line is the only persisted record, and it contains no enactment detail; the only enactment receipts live in workload-side logs (e.g. the sidecar's `[guardrail] kv invalidate: prefix cache reset`) and in mutations themselves (the epoch annotation). For forensics/compliance this is a real gap — a one-line fix (`decisions[i].Note = res.Note` + a field on the audit line) buys a durable, queryable enactment record.
- **F20 — Fixture-side (not Phorvex): the guardrail sidecar's gzip relay quirk (T49 run 1).** The proxy forwarded clients' `Accept-Encoding` upstream but streamed the body raw (`aiter_raw`) while dropping `Content-Encoding` → gzip'd bodies (e.g. `/metrics`) arrived labeled as identity. Chat JSON was unaffected (vLLM only compresses when asked, and plain curl doesn't ask). Fixed in sidecar v3.2 by forcing `accept-encoding: identity` on upstream requests (httpx injects its own gzip default — merely stripping the client's header, v3.1, wasn't enough); metrics through the Service are plain-text again. No Phorvex impact; recorded so the next fixture author doesn't re-derive it.

## Gap-sweep dispositions (the other named MISS classes)

The plan named four representative MISS classes. One (**Chroma poisoning**) was run live as **T7**. The other three are **dispositioned without a redundant live run**, for the honest reasons below — logged so "not run" never reads as "covered."

| MISS class | Disposition | Why not a separate live run |
|---|---|---|
| **litellm SSRF → key theft** (voice B-set; SSRF reaches a secret/IMDS, steals a key) | **≡ T2's verdict class** (static-credential theft) — 🔴 by the same mechanism | T2 already proved live that a stolen key survives pod rotation (5/5 valid). SSRF is just a *different way in* to the same static credential; the Phorvex-side outcome (rotate re-mounts the same Secret; no proactive cred-rotation actuator) is identical. A fresh run would re-demonstrate T2, not a new failure mode. |
| **Denial-of-wallet** (flood/long-hold calls burn STT+LLM+TTS spend — LLM10 / AML.T0034) | 🔴 by architecture — **reasoned, deliberately not run** | Running it live means **actually burning real API spend** (Deepgram/ElevenLabs/LLM) — not justified for a predictable result. Phorvex acts on risk→motion (rotate/quarantine/route-rotate); none of these cap per-call spend or request rate. There is **no rate-limit / concurrency-cap / quota actuator**, and physics (which might see a flood) is GPU-blind for this CPU workload. Fix = edge rate-limiting / concurrency caps / budget guard — an actuator class Phorvex doesn't have. |
| **Voice/LLM prompt-injection** (direct + indirect — LLM01 / AML.T0051) | 🔴 by architecture — **reasoned, not run** | Phorvex never inspects LLM inputs/outputs; there is no payload-inspection path, so *no decision-log entry could ever reference a prompt*. It's a correct MISS *by design* (app-layer concern). Proving it live would only show Phorvex doing nothing — a negative-by-architecture, better stated than staged. (T7's poison is the *indirect* injection variant, and it's covered live.) Fix = a guardrail-proxy at the litellm boundary (input/output classification), app-side. |

**Takeaway across the sweep:** every MISS reduces to one of three durable-substrate classes — **static credentials**, **data-at-rest/content**, or **app-layer semantics/spend** — none of which pod-motion can reach. This is the actuator-roadmap boundary, now evidenced rather than asserted.
