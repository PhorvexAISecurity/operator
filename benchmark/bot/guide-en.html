01

What does the bot do?

Parameter sweeps, bounded code changes, and configured Cost/History comparisons.

The bot has three workflows: /param compares parameter values using the deployed brain; /bench generates a bounded code change and replays it on recorded states; a study file compares reference Cost/History algorithms with explicit arms and seeds.

Identify the experiment type first.Replay evaluates decisions on past snapshots. A study compares registered reference algorithms on explicit recorded or synthetic inputs. Neither alone establishes live defense rates, realized cost or verified coverage for counterfactual decisions.

The bot does not apply these changes to the live brain. Retain the report, configuration and evidence type together. For Cost and History, start with the dynamic-study walkthrough.

04

Change parameters with /param

Explore a supported override without editing code.

1

Choose the parameter and hypothesis

Example: “If I change the allowed cost ceiling, how do selected moves and estimated disruption cost change?” P-FEA-006, the CHi cost ceiling, is relevant to that question.

The ceiling is in normalized disruption units, not dollars. A lower value makes the cost gate stricter; a higher value makes it more permissive. This relationship alone does not establish better defense.

2

Run a small comparison

Example experiment · up to 64 cached ticks
/param P-FEA-006 1.0 1.2 1.5 policy=vllm/vllm-defense ticks=64 nosync

The bot automatically adds a control arm using the recorded effective value and replays each value you supplied as another arm. You do not need to enter the control value. Do not assume that 1.2 is the current value without checking the report.

Use ASCII digits and a decimal point. Each command accepts 1–11 experiment values. All numbers in this guide are examples, not recommendations for configuring the live brain.

3

Read the report, then increase the sample

Check status, actual sample size, and each value against the control. If the data and result are interpretable, try a larger sample. This example also syncs fresh data:

Larger sample with a fresh sync
/param P-FEA-006 1.0 1.2 1.5 policy=vllm/vllm-defense ticks=500

The sample or baseline revision may change between runs. Read every experiment against its own control. Check the cohort and commit before comparing numbers from separate reports.

Known parameters and their limits

IDMeaning and unitDomain and limitations
P-FEA-006CHi ceiling; normalized disruptionGreater than 0, up to 1000. No unset override.
P-FEA-005Proactive hygiene cadence; secondsWhole seconds from 1 to 604800. The override changes both cadence and exposure-pressure scale. Fresh trusted event evidence can bypass the cadence gate.
P-OBJ-003Fixed disruption aversion, or beta0–10 and unset. Incompatible with costPreferences; preflight can return MODE_CONFLICT.
Second example · 5, 15 and 30 minutes, expressed in seconds
/param P-FEA-005 300 900 1800 policy=vllm/vllm-defense ticks=64 nosync

An ID in the registry does not mean every parameter can be overridden. The replay binary must support it and preflight must accept it. This cadence example is not a uniform throttle on every attack response.

05

Change code and formulas with /bench

Turn a clear hypothesis into a patch, tests, and a three-arm comparison.

Use study JSON for the registered Cost/History experiments.This chapter is about changing brain code. Its 20% norm-multiplier example does not implement the endpoint-second model or History v1.1. Study walkthrough
/bench takes a description of a change.In the current interface, you describe what to change and a model generates a diff. There is no direct branch or commit selector, uploaded-diff execution, or /rerun command.
1

Define one question you can evaluate

A useful example: “If I increase the norm term's weight in the cost penalty by 20%, does estimated disruption cost decrease? What happens to selected moves, predicted coverage, and no-op under attack?”

“Make the brain better” leaves the scope and evaluation unclear. Limit your first experiment to one function or condition. If you do not know the file or function, locate it in the source for the baseline revision first.

2

Include these five parts in the request

PartCost-penalty example
Locationphorvex/internal/model/economics.go, function EconomicsMetadata.CostPenalty
ModeOnly independent-cost-preferences-v1
New formula or behaviorChange the norm multiplier from 1 to 1.2; keep the flow term as it is.
ConstraintsPreserve legacy and fixed-beta behavior, feasibility gates, SLO checks, and budgets.
Change sizeKeep the patch minimal, without unrelated edits or broad refactoring.

Use exact file paths, function names and code identifiers. The technical English examples help retrieve relevant context. A fully Persian request without code identifiers may retrieve too little useful context. Verify the example's path and formula against your baseline commit.

3

State the old and new formulas explicitly

This is an example of defining an experiment. The suitability of 1.2 and whether the change passes existing tests have not been established.

Before · only in independent-cost-preferences-v1 mode

penalty = w_norm * norm + w_flow * flow

After · increase the norm contribution to the penalty by 20%

penalty = 1.2 * w_norm * norm + w_flow * flow

For arithmetic illustration only: with w_norm=0.5, norm=2, w_flow=0.3 and flow=1, the penalty increases from 1.3 to 1.5. This describes the expression itself. The brain's move count or final estimated cost will not necessarily change by 20%.

Send the complete command as one message

Preserve legacy and fixed-beta behavior, feasibility gates, SLO checks and budgets. Keep the patch minimal.
Put options before the change description.The order is /bench, then policy=..., ticks=... and optionally nosync, followed by the description. Options at the end can be interpreted as part of the model request instead.

To refresh data and the replay identity before the experiment, omit nosync. Use the command builder to change the sample size or other options.

5

Follow the execution stages

The bot gives you a job ID and reports progress. One job runs at a time; up to five can wait in the queue. Cold builds and tests can take several minutes. There is no fixed completion time.

Check the current job and queue
/status
StageWhat the bot does
Baseline and data selectionChecks replay identity and SHA256, selects ticks from the matching commit, and freezes the selected data for this experiment.
Patch generationThe model proposes a change against the baseline commit. The candidate is created in a temporary clone.
TestsRuns Go tests on both versions: internal/decision, cmd/brain-replay, and changed packages. This is not the full repository CI suite.
BuildBuilds baseline and candidate replays. Both use the same compiler release, read from the deployed binary's build metadata.

A failed test stops the job before the numerical benchmark.If baseline or candidate tests fail, the bot sends the corresponding log. An intentional formula change can conflict with an existing numerical contract. Do not remove or bypass tests merely to get a benchmark result.

Keep all four outputs together

FileWhat to inspect
report-<job>.htmlStatus, commits, data coverage, fidelity, and comparison metrics

Every /bench request starts independently.A second command does not continue the first candidate. It creates a fresh candidate from the baseline commit. Resending the same description with ticks=500 does not guarantee the same patch. Compare the diffs. Replaying a fixed candidate deterministically requires a separate engineering workflow.

First run: check the pipeline without changing behavior

To exercise patch generation, tests, builds and report delivery, request a comment-only change. This is a pipeline check, not an optimization. Conceptually, zero changed decisions is the expected result.

Pipeline check · add a comment only
/bench policy=vllm/vllm-defense ticks=64 nosync In phorvex/internal/decision/ablation.go, add one explanatory comment immediately before the existing if base.Ratio > 0 branch, explaining that the positive-ratio check avoids division by zero. Change comments only. Preserve all executable code and behavior.

Allowed candidate scope: Go files under phorvex/, excluding phorvex/tools/. New _test.go files may be added; existing tests cannot be changed, deleted or renamed. Dependency, go.mod, chart and Dockerfile changes, and file deletions are not accepted by this workflow.

3

Validate first, or upload to execute

Save the example text in a file and attach it as a document in the bot chat, rather than pasting the whole file as a text message. To inspect it without running anything, put /validate in the file's caption. To run it automatically after validation, send the document with an empty caption.

What you sendWhat happens
Valid file, empty captionThe whole file is parsed and validated, then queued as one batch.
Valid file, /validate captionStructure and parameter domains are checked. No experiment is queued.
File with one invalid section/valueRejected with an error and line number where available. Nothing is queued.
File containing only bench or only paramsOnly the supplied valid section is executed.
Malformed Word, oversized file, unsupported typeRejected; use the supplied examples or export a fresh .docx/.txt.
Put /validate on the attachment itself.Sending /validate as a separate message only displays instructions. It does not change the mode of the next upload. Keep section names, option keys, IDs and numeric digits exactly as shown in the examples.

Structural validation checks format, options, parameter IDs and registry value domains. It cannot establish that a proposed code change compiles or passes tests. Each experiment still runs its Go tests and/or runtime replay preflight.

4

Follow the batch and collect its results

One batch can contain up to five experiments. They execute sequentially on the host. Each experiment returns its usual report files; the batch also returns JSON and CSV summaries with job IDs and statuses. A runtime failure is reported and other independent experiments continue. Use /cancel to cancel the running batch and skip its remaining experiments.

Progress stays visible while work runs.A single editable activity card shows the current task, elapsed time and batch experiment number. It refreshes every eight seconds while waiting for a model, tests, builds or replay. The moving bar is an activity indicator, without an invented percentage or ETA. Terminal states include DONE, PARTIAL, NEEDS_DATA, FAILED, CANCELLED and INTERRUPTED.
Illustrative activity card; not a live job

[□□■■■□□□□□] Experiment 2/3 (bench): running Go unit tests: candidate

Activity indicator; no completion-time estimate.

PARTIAL in a batch summary means some experiments succeeded and others failed. PARTIAL in an individual experiment report refers to incomplete data coverage. Read these statuses separately.

Caption spelling matters.Use /validate with a forward slash. An unknown caption, including \validate, is rejected without downloading or queuing. Use an empty caption to run.

07

Dynamic Cost and History benchmarks

One JSON file: configured comparison arms, recorded seeds and shared reports, without code generation.

This workflow is deployed.A study executes registered reference algorithms using the supplied configuration. Change arms, selector settings and seeds without asking a model for another patch. A new, unregistered algorithm still requires implementation.

1. Choose one of the three ready-made files

Send /templates. Start with a synthetic example to learn the workflow. /study displays help; attaching the JSON file starts an experiment.

FileComparisonEvidence
study-cost-synthetic.jsonLegacy versus endpoint-v1 cost, the same deterministic B=1 selector, three seedsSynthetic; 6 arm/seed runs
study-history-synthetic.jsonDeterministic, entropy, score-only stochastic and history-weighted selectors; three seedsSynthetic; 12 arm/seed runs
study-history-recorded.jsonThe same four selectors on a prepared recorded datasetRecorded; requires a valid trace and ledgers
A synthetic example is not a production outcome.The two synthetic files demonstrate computation and history behavior. The recorded request returns NEEDS_DATA until the required evidence is installed. Existing legacy snapshots or an all-PASS /check do not establish that these ledgers are available.

2. Configure and validate the request

Download a file from the builder below, or edit its JSON. Preserve the keys and identifiers. Attach it with /validate as the caption; after PASS, attach the same file with an empty caption to run.

SettingMeaning
arms1–8 named arms. The first arm is the decision-comparison reference; all arms share the input trace.
seeds1–16 distinct integers. With identical input, configuration and implementation, draws are reproducible.
epsilonMaximum expected score loss, not a guarantee for each draw. Zero permits only maximal-score choices.
history.window_secondsCounter lookback window; it does not alter the mandatory 24-hour coverage contract.

Limits: 2 MiB per JSON file, up to 5,000 ticks and 100,000 candidate rows across all arms and seeds. Do not wrap JSON in [bench]. Legacy ticks and sync are not top-level study fields.

3. Choose the cost model and selector

ChoiceMeaning
cost.kind: providedConsume authoritative c and rho inputs; useful for isolating selectors with a fixed cost estimator.
cost.kind: legacyCombine supplied norm/flow terms with explicit weights and a chi gate. Values are dimensionless.
cost.kind: endpoint-v1Duration estimates and endpoint-second reservations, including cold/censored data and quarantine-specific accounting.
selector.kinddeterministic, entropy or history. The History example includes a score-only arm with history weights set to zero.

For a History comparison, hold cost and gates fixed across selectors. For a Cost comparison, hold selector and move count fixed. This workflow uses B=1. Example parameters are study choices, not approved production defaults.

4. Supply meaningful history and recorded evidence

  • F counts actual optional opportunities after gates; a retry is not another opportunity.
  • S counts acknowledged execution starts. A draw, failed dispatch or proposed choice does not increment S.
  • Security effects require matching verified events. An apparently successful action does not automatically earn verified coverage.
  • Each arm/seed has isolated history. In observed mode, counterfactual choices do not generate actual execution events.
  • Missing required history triggers deterministic PICKER_UNAVAILABLE fallback and PARTIAL. Missing cost accounting is not initialized to unused budget.

For recorded mode, the data owner must prepare and import chronological identities, gate verdicts, budgets, duration samples and valid history events. Renaming synthetic data does not make it recorded evidence. This reference runner consumes the required gate/scheduler verdicts; it does not rerun production schedulers or actuators.

Establish comparison validity, examine metric changes, then assess your hypothesis.

2

Understand the three /bench arms

control

The deployed replay binary

A tick is control-eligible only if this binary exactly reproduces the recorded production output.

base-local

The baseline source, built here

For a valid comparison, fidelity must be EXACT and its changed-decision share against control must be zero.

candidate

The code generated for your request

This is a different brain revision. Its results are labeled OBSERVATIONAL.

If base-local is DIVERGED, do not use the candidate result to make a decision.First establish why the local baseline differs from the deployed binary. EXACT describes decision reproduction on the inspected ticks; it does not by itself guarantee that both binary files are byte-identical.

/param normally reports MATCHED_REPLAY. OBSERVATIONAL is expected for /bench because it compares different source revisions.

3

Read the metrics against your experiment question

IDWhat it measuresHow to interpret it
M-P21Share of ticks whose selected action set differs from controlBehavioral sensitivity, with no inherent good/bad direction. It is not an improvement score.
M-P26Selected moves per tickA reduction may remove unnecessary moves or omit a needed response.
M-P28Estimated disruption cost of selected movesA cost-model estimate, not measured live disruption or money spent.

Does any Word document or long description become a benchmark?

No. Use valid code/parameter sections or a versioned study JSON request. Unregistered algorithms require implementation.

Does a study run the production brain?

A study runs reference algorithms on explicit inputs. Its report identifies mode=REFERENCE_STUDY and evidence type. Live outcome claims need suitable evidence.

How do I repeat a study?

Reuse the same request, data, seeds and implementation. A server dataset can change; retain the frozen resolved-request.json from evidence.zip.

Does /validate guarantee study success?

It checks structure, limits and supplied trace shape. Server dataset availability and evidence completeness are checked at execution. PASS can later lead to NEEDS_DATA or PARTIAL.

Does /validate compile code or run Go tests?

No. The /validate attachment caption checks file structure, options, parameter IDs and value domains, without queuing an experiment. Send the file with an empty caption to execute it. Go tests and replay preflight apply to code/parameter workflows. Studies use their own schema and evidence checks.

Do bench and params in one file apply the values to the new code?

Each section creates independent experiments with their own controls and reports, executed in file order. Parameter values are compared using the baseline replay binary. Testing a fixed candidate with parameter overrides requires a separate engineering workflow.

Why does the activity bar not show a percentage?

Model, test, build and replay durations are not known in advance. The card shows the actual stage and elapsed time with an activity indicator, refreshing every eight seconds while running. It records the terminal state when work finishes, fails, is cancelled or is interrupted by a restart.

Can I say “run the previous candidate again with 500 ticks”?

Not through the current interface. Each /bench request is independent and the model regenerates a patch. Identical descriptions do not guarantee identical diffs. Compare the diff, baseline and data between runs. There is no /rerun command.

Can I describe the change entirely in Persian?

You can write a Persian description, but include exact file paths, function names and English code identifiers. Context retrieval currently relies on ASCII identifiers. A fully Persian description may retrieve too little useful context. The technical English examples in this guide are a more reliable way to specify the request.

Will the bot update old tests when a formula changes?

No. Existing _test.go files are immutable. The bot may add a new test file for a new helper; it does not rewrite old tests to make a change pass. Establish whether the new code is wrong or the intended product contract is changing. A contract and test change needs separate review. The bot reports the failure log and stops before benchmarking.

Do passing tests approve the entire brain and release?

No. These targeted tests do not cover the full CI suite, every package, or live tests. Review the diff, evidence quality, relevant metrics, and live effects in proportion to the change.

Zero changed decisions: does that mean the formula has no effect?

It only means the selected action set did not differ on this experiment's valid ticks. The changed path may not have been active, another gate may have determined the result, rankings may have stayed the same, or the sample may be uninformative. Inspect the diff and experiment context first.

How do I open the HTML report?

Download the report from Telegram and open it in a browser. Use the CSV in Excel or a data tool; read the diff in a text editor. This guide is also a self-contained file and can be read offline.

Will repeated experiments with 1.2 always give the same result?

The data, baseline identity and selected sample can change between runs, especially after syncing. With /bench, the patch is also regenerated. Compare runs using their job IDs, commits, diffs and cohorts.

What happens after I find a promising candidate?

The bot does not publish the change. Take the diff and evidence through code review, CI, and live evaluation appropriate to the change's risk. This stage gives you concrete evidence for that decision. Replay alone does not authorize applying the candidate to production.
