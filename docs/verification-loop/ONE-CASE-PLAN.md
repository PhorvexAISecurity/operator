# Verification loop: first reproducible case

## Authorized scope and source

The owner approved one reproducible loop on 10 October 2026, using GPT-6.1 Sol
implementation and review agents. The repository was first fast-forwarded to
`main` commit `54c9273a6faaa3768e55adf15afb51de68b3241b` (PR #449).

This is a bounded implementation of the verification-loop architecture, not a
restart of earlier catalogue campaigns. The loop uses an isolated local API
server and local serving processes. It changes no shared cluster resource and
introduces no LLM into the production decision engine.

The lead owns the case contract and final disposition. An implementation worker
owns the Go driver; a separate worker owns the runtime launcher. A third agent
independently reviews and reruns the delivered implementation. No contributor
may certify their own implementation as independently reviewed.

## Case and threat

The case is future reuse of a stolen inference caller credential. Two owned
synthetic credentials start authorized: A represents the stolen credential and
B the legitimate caller. A successful HTTP inference request with A establishes
the attack baseline. After Phorvex responds, the identical credential A must be
denied while B continues performing the same operation.

The response is the existing `endpoint-lease-revoke` actuator. It revokes a
specific source-bound caller lease. This is distinct from `endpoint-rotate`:
changing a route selector does not revoke a known credential or stable address.
An earlier successful disclosure is recorded and cannot be undone by revocation.

The inference body is produced by a declared deterministic synthetic downstream
application. The authorization boundary is the unchanged shipped Python
`EndpointLease` and `ServingBoundary`. The case does not test GPU inference,
model reasoning, classification or autonomous attack detection.

The configured recon profile is `ucw-recon`, as explicitly configured by the
manager. The local case declares a one-second anti-over-rotation window and waits
for actual Pod identity age to clear it. All other selection evidence is recorded;
the policy stays fixed across clean, stale and attack controls. This configuration
does not certify behavior under a production five-minute window. An initial
fixture attempt using the default `standard-recon` and a five-minute window
declined, because the typed lease fact was not scored and the actual new Pod was
too young. That unsuccessful attempt is preserved as fixture-design evidence;
neither the brain nor the Pod's observed age was rewritten to force a result.

## Required chain

1. Launch a private Kubernetes API server and etcd using the repository's pinned
   envtest assets. Never load a user's kubeconfig or connect to a shared cluster.
2. Create current policy, source, caller Secret, serving identity, Service,
   EndpointSlice and protected journal objects. Kubernetes supplies real UIDs
   and resource versions; resource-version updates use actual API semantics.
3. Start the unchanged caller-admission boundary over actual HTTP and a private
   TLS status listener. It reads the effective policy and caller Secret from the
   same private API server to which the native actuator writes.
4. Probe A and B through the public application route. Preserve response hashes
   and actual downstream invocation evidence. Both must succeed at baseline.
5. Produce an explicitly disclosed `TEST_INJECTED`, exact-target observation
   from those responses. Apply the normal trust and observation admission path.
6. Evaluate the unchanged brain using `DecideShadowChecked`, a fresh isolated
   owner, a frozen decision clock and the actual native capability checks.
   Candidate policy stays fixed throughout the trial; no expected action is
   forced. Preserve the complete validated decision trace and all exclusions.
7. Dispatch only the action genuinely selected, using `NativeActuator.Actuate`
   with secure serving authority. Preserve the journal and effective policy
   revision generated by the native operation.
8. Repeat A's request: require the specific `401 unauthorized` admission result
   and prove it did not invoke the downstream operation. A timeout, disconnect
   or `503 lease_unavailable` is a failed/unknown trial, never a defense.
9. Repeat B's operation during and after dispatch and over a bounded hold window.
   Preserve request counts, failures and elapsed time against the declared local
   probe budget. Collect an actual wall-clock containment interval separately
   from the frozen brain clock.
10. Run a clean no-attack control using the same initial case contract without
    the attack observation. It must not select lease revocation or mutate its
    enforcement policy. A no-actuation baseline must leave A authorized.
11. Re-evaluate the exact recorded decision input, identities, clock and owner
    state in a fresh brain. Canonical traces must match exactly. Separately run
    a fresh physical episode to check repeatability of behavioral outcomes;
    generated API identities must not be normalized into a claim of exact replay.
12. Tear down API servers, listeners, subprocesses and temporary credentials,
    including on cancellation or failed prerequisites. Retain only non-secret
    evidence, source hashes, errors and measured outcomes.

## Verdict boundaries

| Observation | Required result |
| --- | --- |
| A succeeds, brain selects the matching response, native revocation completes, A then receives a specific denial, B's sampled controls pass | `LOCAL_RUNTIME_DEFENDED`, scoped to future credential reuse and this local experiment |
| A still succeeds after a completed trial | `LANDED`, with the first failing stage |
| No relevant selected response | `DECLINED`, preserving the actual candidate reasons |
| Missing authority, timeout, invalid control, drift, incomplete readback or failed replay | `INCOMPLETE`; no defense credit |
| Baseline A is already denied | `NOT_LANDED`; no fresh brain-defense credit |

The existing formal SLO registry classifies endpoint lease revocation as
`unknown`, because no complete safe-return bound is registered. Measured local
legitimate-service success must not turn that analytic classification into zero
or a production guarantee. The output records both fields separately:
sampled local availability and formal SLO-bound status. A local defended result
is not a full architecture WIN or an unrestricted deployment approval.

No claim is made about a real kubelet, CNI, container image membership,
controller-driven Pod readiness, projection lifecycle, production RBAC, GPU
hardware, co-tenant resource contention or the whole customer attack surface.
Kubernetes serving metadata is an explicit fixture representing the local
processes, not an attestation that containers were deployed.

## Acceptance and failure controls

- Real successful attacker and legitimate baselines; exact response provenance.
- Real brain selection and full native dispatch, not a direct handler call or
  synthesized success response.
- Independent attacker/legitimate probes against the application, not merely
  an epoch, ConfigMap or operation receipt.
- Clean-control non-selection and unchanged enforcement state.
- Fresh-episode behavioral repeatability and exact-input decision replay.
- A skipped revocation must fail the defense oracle; unavailable authority must
  fail rather than masquerade as denial; a changed replay trace must be detected.
- Bounded execution, cancellation cleanup, private temporary credentials and
  hashed non-secret evidence.

Phase one delivers this case and its round ledger. No broad agent swarm,
additional catalogue entries, automatic learning promotion or unrelated product
repair is included. Any wider campaign requires its own workload contracts and
evidence.
