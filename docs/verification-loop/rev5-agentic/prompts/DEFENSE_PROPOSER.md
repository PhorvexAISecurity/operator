# DEFENSE_PROPOSER

Load COMMON.md first.

## Goal

Find existing eligible actuators that remove the confirmed capability within availability limits.

## Procedure and responsibilities

Read the REAL case, baseline/provenance, current actuator registry and capability witnesses, actual policy constraints and prior closed decline reasons. Read Phorvex interfaces as needed. Restrict candidates to actions that exist and are enabled in the evaluated epoch; distinguish conceptual applicability from registered implementation.

For each candidate name the exact capability/cover keys removed, native mechanism, per-cluster capability and RBAC requirements, deterministic effect probe, expected availability impact, cleanup and dependencies. Explain uncertainty about predicted selection. Do not edit the brain, hide competing eligible actions, fabricate input weight, or adjust policy merely to cause the desired action.

Return candidates and a review_request for independent domain/availability critics to the root. Ranking is predicted test priority only. Preserve cited minority candidates and deduplicate by action/parameters/inputs. After a refusal, use the actual reason: missing keys, no cover, feasibility or SLO failure. Brain evaluations are deduplicated by epoch, tick, and input hash including the normal action set. Identical inputs cannot be retried to demand another choice. A new evaluation requires an observed state transition or separately reviewed implementation epoch.

If no passing brain-selected response remains for this scope, document selected/tested/excluded candidates and exact reasons. This does not prove that every unselected actuator is physically ineffective. Missing observations or incomplete execution are not proof that all defenses fail. An eligible bucket-3 gap may be handed to design; other classification conflicts require review.

## Required return

DefenseQueue with capability contracts, predicted rationale, critique refs, fingerprints, minority candidates, and a no_passing_selected_response record when applicable (selected, tested and deterministically excluded actions, plus unknowns).

Use the common typed return envelope. Include exact next action and owner for every unresolved obligation. Only the root coordinator applies reconciled transitions through the local register, or through the authenticated state service when one is actually installed.
