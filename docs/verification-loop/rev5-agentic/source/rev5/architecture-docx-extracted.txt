1. What this package is (read this first)

Phorvex is “the deterministic intelligence layer”: every shipped belief is a closed-form, explainable number, with no LLM in the belief path [DOC-CITED killchain/conjugate.go:5-11]. The verification loop introduces LLM agents for the first time — without weakening that guarantee — by making the agents a pure *generator of ideas* and the existing deterministic engine the *discriminator* that decides truth.

The core idea is a competition. Attack agents and actuator agents play adversarial rounds on an isolated twin. Each round: attack agents propose, a deterministic gate confirms which attacks are *real*, actuator agents propose defences, and the real brain decides which actuator truly defends (selects it, feasibility accepts, effect confirmed, availability holds). Then — crucially — the attack agents attack again, this time against the winning actuators, searching for a new real path around them. Rounds repeat until no deterministically-confirmed attack gets through, or the result is an honest CANNOT-HELP. Every proven (attack, actuator, brain-verdict) triple is stored as the per-customer RL learning record, shadow only. The whole thing is automated and plug-and-play; only final approval is human.

How it was produced (and reconciled). Seven independent workstreams (WS-1…WS-7) ran in parallel, read-only, each grounding its design in cited code; this package reconciles them with disagreements stated, not averaged. There was exactly one: WS-3 presents the ‘actuator works’ checks as separately-named gates while WS-4 presents them as a fused selection step — both describe the same mechanism at different granularity, reconciled in §7.1 (the live engine fuses capability+feasibility+SLO into selection; the validator decomposes them for audit).

The ten things this package delivers (per the brief’s §0)

1. The agent architecture — the two halves (generator / validator) and the deterministic brain as referee between them (§5–§8).

2. The adversarial competition — the central round-by-round loop, attacker re-attacking the winners until no real attack gets through or CANNOT-HELP (§3).

3. The roster and its sizing rule — personas, how they nest, and the rule that derives *how many* from the scan (tens for small, low hundreds for large; never a fixed 500/1000) (§4).

4. The consensus / deliberation protocol — how teams propose, critique, merge, rank and learn from decline reasons to converge faster; agreement selects *what to test*, never approves (§9).

5. The brain-in-the-loop protocol — isolated twin, real brain replay, explainability read, effect + availability confirmation (§10).

6. The actuator verdict — seven measured metrics (three gates + four scores), their four rules, and the build order (§8).

7. Plug-and-play instantiation + safety rails — scan any cloud → size → compete → recommend; brain unmodified, no production attack, availability a gate (§2, §4).

3. The adversarial competition — the central loop

This is the heart of the design. The generator and validator do not run once; they compete over rounds, and the attacker is obliged to come back and beat the defender that just won.

3.1 One round

1. Attack agents propose. The generator roster (§5) emits HYPOTHESIZED attack fragments against the current cluster twin — and, from round 2 onward, specifically against the *winning actuator set* already in place.

2. Deterministic gate confirms real. The ‘attack is real’ gate (§6, checks C1–C6) promotes a fragment to REAL only when every precondition is confirmed against scanned facts. Unconfirmed → HYPOTHESIZED → quarantined. Agent agreement is never evidence.

3. Actuator agents propose. For each REAL attack, the validator roster (§7) proposes candidate actuators.

4. The real brain decides. On the isolated twin (DecideShadowChecked), an actuator wins only if the brain SELECTS it AND feasibility ACCEPTS it AND the deterministic probe confirms the attacker capability is GONE AND availability HOLDS for every affected workload including co-tenants [DOC-CITED coverage.go:557-567; feasibility/constraint.go:44-69; adapter_rotate.go:314-320; slo/bound.go:199-215].

5. Store the proven triple. Each winning (attack, actuator, brain-verdict) — with the brain’s explanation quoted exactly and the seven metrics (§8) attached — is appended to the per-customer RL record, shadow only (§11).

6. Next round: re-attack the winners. The winning actuators become part of the twin’s defended state, and the attack agents search for a new real path *around* them. The loop repeats.

3.2 Termination (bounded, deterministic, honest)

The competition ends when either (a) a full attack round against the current winning actuator set yields no deterministically-confirmed attack that gets through — the defended state is *stable under adversarial re-attack*; or (b) for the latest confirmed attack no actuator is selected-and-confirmed without breaking availability or the brain — an honest CANNOT-HELP for that attack. A configurable max-rounds budget guarantees termination even if the attacker keeps finding marginal new paths; reaching it is reported honestly as ‘not stabilised within budget’, never as a false win [INFERRED from the closed classifier, audit/log.go:924-940].

3.3 The round-by-round record (an output artifact)

The loop emits a round ledger the founder can read top to bottom:

3.4 When no existing actuator works: actuator design by agents

Trigger. The competition reaches CANNOT-HELP for a confirmed real attack: no enabled actuator is selected-and-confirmed by the brain without breaking availability. Instead of stopping there, the loop opens a design round. This is the actuator-synthesis half of the original objective (a new actuator that provably defends each attack), not a pick from a fixed list.

Who proposes. Design agents, one persona per enforcement level, sized from the scan exactly as the attack and validator rosters are (section 4.2): network / dataplane (CNI, eBPF, flow-drop of established connections, not only deny of new ones), K8s platform, AI/GPU serving, credential, process, artifact. Each proposes a NEW actuator spec at the lowest enforcement level that would truly remove the attacker capability the CANNOT-HELP attack exploits.

How they agree. The same deliberation protocol as section 9 runs over the design proposals: proposers emit specs, critics predict which gate each spec would fail (no cover, infeasible, SLO, not installable), the deterministic aggregator ranks them, and an evidence-bearing minority spec is always kept. Agreement sets the order engineers see; it never approves a spec.

What a spec must contain. Every proposed actuator fills the Actuator Capability Contract: the capability it claims to remove, the exact cover keys it may claim, the enforcement mechanism, the required RBAC/permissions, the per-cluster capability check, the deterministic effect-confirmation probe (how the loop will later prove the capability is gone), the availability impact and rollback, and the determinism statement. A spec that cannot name its confirmation probe is rejected, not ranked low.

What the agents do NOT do. Design agents never write, compile or deploy actuator code, and never touch the brain. The output of a design round is a ranked list of actuator specs handed to the AI and platform engineers. The brain stays unchanged; no LLM is ever in the decision path.

Closing the loop. Once engineers build a proposed actuator and register it behind the existing Actuator interface, it becomes an ordinary enabled actuator: it re-enters the competition, the attack agents re-attack the defended state, and it must clear the same seven-metric verdict (section 8) and be re-attacked until STABLE. A built actuator that still fails its gates returns an honest CANNOT-HELP — the design round widens the actuator set, it never lowers the bar.

4. Plug-and-play scan & dynamic roster sizing (WS-1)

“PX-SCAN-01” is the brief’s name for the scan boundary; the literal string is not in the repo [UNVERIFIED]. It maps to the real boundary: currentinventory + currentobserver (protected-asset observation) + epssfeed (image inventory + Trivy + EPSS) + recon (the fact/cover universe), assembled into one model.WorkloadView per pod per tick [DOC-CITED recon/profile.go:18; model/types.go:1105].

4.1 What the scan yields (and how it maps to agents)

The scan discovers pods, running containers, unique images, EPSS/CVSS pairs per digest, served models (ModelID), endpoints/routes, RBAC/identity (ServiceAccount, PodBoundKubeAPIAuth, MountedSecrets), GPU/MIG, lateral edges/blast radius, nodes/co-residency, named attack-vector observations, and the “app” unit = StableWorkloadOwner [DOC-CITED epssfeed/sync.go:57-78; model/types.go:454-560,1114-1116; currentinventory/contract.go:47]. It derives two universes the roster mirrors: the weighted fact-universe (recon/ucw.go) and the cover-universe — cover is granted ONLY where an actuator can prove invalidation; audit-only and Tier-2/3 facts carry no cover [DOC-CITED recon/facts.go:63-150; recon/taxonomy_test.go:69-107].

Kill-chain stages: 9 — 5 generic + 4 AI, honest-absent when ModelID==“” && !HasGPU [DOC-CITED killchain/hazard.go:19-36]. Cover-granting actuators: 17 of the 23 MutatingActions; a nil policy defaults to rotate+quarantine only [DOC-CITED model/types.go:159-174].

4.2 The sizing formula (derived, never a fixed count)

Let Apps = distinct StableWorkloadOwners. For app a: |S(a)| = applicable kill-chain stages ∈ [5,9]; V(a) = observed named attack vectors; K(a) = cover-granting actuators for a’s archetype ∈ [2,17].

Generators G = Σ_a ( |S(a)| + w_v·|V(a)| ) # per stage × per app, + live-vector boost

Validators Val = Σ_a |K(a)| # per cover-granting actuator × per app

Total R = G + Val

Floor R_floor = 7 (1 generic app, nil policy: G=5, Val=2)

Safety cap R ≤ λ·(ObservedPods + UniqueImages) # defense-in-depth bound

Design-roster sizing (Rev 4). Design agents are added only when a CANNOT-HELP occurs (section 3.4): Des = Σ over CANNOT-HELP attacks of the enforcement levels that attack spans (network/dataplane, K8s, AI/GPU, credential, process, artifact), so a cluster with no CANNOT-HELP spawns zero design agents, and a large cluster spawns them only where an attack is genuinely uncontained. R = G + Val + Des. The envelope stays tens for a small cluster and low hundreds for a large one, derived from the scan, never a fixed count.

Sizing law. w_v and λ are configurable parameters (§14). Worked: small 3-app cluster ≈ 21 agents (tens); large 40-app/20-AI ≈ low hundreds — capped, never a fixed 500/1000.

Audit-only / Tier-2/3 facts yield ZERO validators — the brain never spins a validator for an effect no actuator can prove; the single largest natural cap on Val [DOC-CITED recon/facts.go:63-150].

4.3 Efficiency budget — three early-stops + three caches

• Absent-asset short-circuit (hard): a pod with any non-finite weight/physics input mints no facts → 0 generators, 0 validators [DOC-CITED recon/profile.go:43,187-204; recon/finite.go:12].

• No-cover short-circuit (hard): facts with no cover-granting actuator are excluded from Val by construction [DOC-CITED recon/facts.go:63-150].

• Marginal-gain stop (soft): generators dispatched in descending fact EMR weight, halted once facts-invalidated-per-dollar < the objective’s cost penalty [DOC-CITED recon/ucw.go:21-48].

• Caches: byte-stable EPSS ConfigMap [DOC-CITED epssfeed/feed.go:235-267]; validator-result cache keyed by archetype so validators run once per archetype, not per pod [INFERRED from recon/cover_invariant.go:53-85]; restart-safe exposure clocks [DOC-CITED exposure/clock.go].

5. Generator (attack) architecture (WS-2)

A four-tier hierarchy. Tiers 0–2 are LLM agents that may only emit HYPOTHESIZED scenario fragments; tier 3 chains them; the gate (§6) is not an agent. No agent can set a scenario’s status to REAL [INFERRED].

Tier | Who | What they emit

T0 | Offensive generalist / orchestrator | Dispatch only; owns the scan snapshot + winning-actuator set, dedupes, holds the HYPOTHESIZED queue

T1 | 8 kill-chain stage specialists (recon, initial-access, execution, persistence, priv-esc, lateral-movement, collection, exfil/impact) | ScenarioFragment per stage, mapped to the shipped Stage enum [hazard.go:19-34]

T2 | Domain specialists (network/SDN, identity/RBAC, supply-chain/CVE, AI-ML, agentic) + per-application specialists spawned only for carriers the scan populated | ScenarioFragment per domain/app

T3 | Cascade strategist | Multi-stage DAGs over confirmed edges, respecting successorOf()/aiNextStage()

A persona emits only a ScenarioFragment = {node, stage, claimed-precondition-facts, claimed-enabling-edge, claimed-CVE?, rationale-text, target-actuator-set?}. The last field is set from round 2 onward so the attacker explicitly aims around the winning actuators. An agent never emits a status, weight, or coverage number — those come from the deterministic layer after the gate [INFERRED; DOC-CITED recon/facts.go:159]. Per-application specialists are spawned only for carrier families the scan populated, so the roster is data-driven and honest-absent [DOC-CITED model/types.go:498-500].

6. The deterministic “attack is real” gate (WS-2)

A ScenarioFragment (and transitively a cascade) is REAL iff every precondition it claims is independently confirmed by a deterministic check against scanned facts. Any unconfirmed precondition keeps it HYPOTHESIZED and quarantined. LLM confidence, multi-agent consensus, and derived urgency are inadmissible [INFERRED from killchain/hazard.go:97-102]. The gate is a pure function, side-effect-free, matching the reachability engine’s proven no-mutation contract [DOC-CITED reachability_optimization_test.go:38-75].

Check | Claim it confirms | Deterministic oracle (verified)

C1 Reachability edge | A can reach B | graph.edgeExists = RBAC-lateral OR co-location OR (A egress∧B ingress); safe over-approximation [reachability.go:144-165,12-16]

C2 RBAC capability | A’s identity can exec / write pods / read secrets / impersonate | ResolveRBAC→SubjectPerms + scope bit [rbac.go:50-98,141-178]

C3 Precondition facts | fact F exists on node N | recon.AssetFacts contains F.Key(); non-finite⇒no fact; Tier-3/audit-only confirm as evidence but are uncurable [recon/facts.go:140-202]

C4 CVE exploitability | image digest D exploitable via CVE X | epssfeed cache Entry for D; absent≠safe; provenance ≤7d, Complete iff FailedImages==0 [epssfeed/feed.go:13-233; epssmeta/metadata.go:26-110]

C5 Kill-chain evidence | node N is at stage S / attacker holds N | killchain.Assess with HasEvidence/HasEventEvidence — a real observation, NOT StageUrgency; GPU theft/side-channel unavailable absent a device-bound contract [killchain/hazard.go:160-175,284-333]

C6 Source trust | every event the agents cite | authenticated allowlisted creator (TrustTrusted), not a self-declared source; empty allowlist fails closed [ingest/eventtrust.go:13-39]

Quarantine retains HYPOTHESIZED fragments (not deletes), zero coverage weight, re-evaluated every round — if a later scan or a later round populates the missing fact/edge/CVE, the same fragment promotes without re-invoking the LLM [INFERRED from reachability_optimization_test.go:102-123]. Each quarantined item records *why* each precondition failed.

6.1 Scanned content is UNTRUSTED data (prompt-injection defence)

Scanned text (image metadata, annotations, ConfigMap bodies, MCP tool descriptors, Voice memory) is attacker-influenceable — the repo already saw a self-named detector source steer the brain [DOC-CITED ingest/eventtrust.go:17-23]. Defence: scanned content is passed to agents strictly as quoted inert data, never in the instruction channel; because agents can only produce HYPOTHESIZED fragments and every REAL promotion needs a deterministic oracle, an injection string can at most cause a *hypothesis* the gate then fails to confirm — no path to REAL, coverage weight, or selection; content-derived facts must bind to authenticated content-hashed witnesses; agent output is parsed into the fixed ScenarioFragment schema [INFERRED; DOC-CITED model/types.go:581-600].

7. Validator architecture & the “actuator works” gate (WS-3)

The validator is a proposer/prover roster *outside* the brain. It proposes actuators and feeds each through the real brain; it never scores defences itself. T0 brain-in-the-loop adjudicator (the only pass/fail authority) → T1 explainability reader → T2 persona proposers (CISO, SRE/availability-veto, network, K8s platform, AI/MLOps, cloud, detection&IR) → T3 prover harness. Each persona is mapped to the code it must respect (e.g. SRE veto → feasibility/defaults.go:44-97 + slo/bound.go:199-215; detection&IR owns the capability-gone probe adapter_rotate.go:404-410) [DOC-CITED].

Why a probe + control run are needed: completeness is build-enforced, but its own stated limit is that “a handler that returns success while doing nothing still satisfies the registration tier” [DOC-CITED actuator/completeness_test.go:14-20]. Registration is not proof of defence — hence the capability-gone probe and the clean no-attack control run (§8).

7.1 The “actuator works” gate — an ordered deterministic pipeline on the twin

Stage | Gate | PASS condition (verified)

0 | Capability / no-cover admission (pre-scoring) | capability.Gate first-failure-wins: not-installable→no-cover→capability-unsupported→no-rbac [capability/gate.go:15-37]

1 | Brain SELECTS it | CoverageEngine.Decide: strictPositiveGain>0 AND existential containment (every RequiredKey ∈ CoverKeys) [coverage.go:557-567; existential.go:99-112]

2 | Feasibility law ACCEPTS it | feasibility.Evaluate first-veto-wins, fail-closed → Feasible==true [feasibility/constraint.go:44-69]

5 | Reproduced across the scenario battery | the verdict must hold on every archetype fixture in the battery (plain / stateful / neighbors / gpu* / sensitive-output / vector-*), with the brain’s explainability parsed each iteration; one failing scenario fails the actuator [docs/recon-cover-map.generated.md:32-59; decision_trace_v3_test.go]

Reconciliation note (fused vs decomposed). In the live engine the brain *fuses* capability + feasibility + conformal-SLO *into* selection within one tick — an infeasible or SLO-gated action is never a selectable candidate — so Stage 1 already implies Stages 2 and 4a [INFERRED]. The validator still evaluates them as *separately-named gates* for auditing and for routing a decline back to the proposer. Stage 3 (probe) and the ledger hold are genuinely post-dispatch.

7.2 The canonical CANNOT-HELP: the endpoint-rotate no-op the brain refuses

The brief’s reference no-op is grounded precisely: endpoint-rotate is *generatable* yet “coverless in every fixture” [DOC-CITED docs/recon-cover-map.generated.md:76], excluded at the no-cover gate before scoring [DOC-CITED capability/m044_route_claim_test.go:74-75], and a negative control makes “endpoint-rotate gained credential invalidation credit” a *test failure* [DOC-CITED actionset/endpoint_lease_test.go:43]. Coverless ⇒ can never contain ⇒ can never be SELECTED — the deterministic restatement of “the brain refuses the no-op.” It is the canonical CANNOT-HELP entry, never ranked low. Coverless companions the brain likewise refuses: route-rotate, guardrail-rotate, debugger, custom-inject, identity-rotate.

7.3 The actuator-design roster (when the validator set is exhausted)

The validator roster in 7.1–7.2 proves actuators that already exist. When every enabled actuator returns CANNOT-HELP for a confirmed attack, the design roster (section 3.4) is the validator half’s synthesis arm: persona agents per enforcement level propose a new actuator spec, lowest-level-that-works first, each spec carrying its Actuator Capability Contract and its deterministic confirmation probe.

The roster is general and scan-driven. It is instantiated per CANNOT-HELP attack, with one proposer per enforcement level the attack spans and critics drawn from the same validator personas (SRE availability veto, network, K8s, AI/MLOps, detection & IR). It proposes specs for any customer’s apps — it never assumes a particular cluster, actuator or cloud. Its output is a ranked spec list for engineers; nothing it proposes is deployed by an agent, and the brain is never changed.

A built spec is then an ordinary actuator: it re-enters the competition, is re-attacked, and must clear the seven-metric verdict (section 8) like any other. This is the only path by which the actuator set grows, and it grows only on proven need.

8. The actuator verdict — seven measured metrics

Every actuator that the brain selects in a round is scored on seven metrics, computed OUTSIDE the brain (the brain is unchanged): three gates and four scores. The gates decide admissibility; the scores order the admissible actuators and feed the RL record. All measured, never estimated.

8.1 The three gates (binary; any fail ⇒ CANNOT-HELP, never a low rank)

# | Gate | PASS condition (measured on the twin)

8.3 The four rules for all seven metrics

1. A metric can only fail an actuator, never pass one the brain did not select. Brain selection is a precondition; metrics are strictly subtractive. A metric never promotes an action the brain excluded.

2. A metric that cannot be measured is ‘unknown’, never zero or pass. Mirrors the engine’s own rule — ‘Unknown must never be serialized as a numeric zero’ [DOC-CITED slo/bound.go:28-31]. An ‘unknown’ gate blocks; an ‘unknown’ score is carried as unknown, not a win.

3. Metrics reach the brain only through the RL record as shadow proposals with human approval — never directly. No metric is wired into Decide; the brain is unchanged. Promotion is the human Approve gate (AutoEscalate()==false) [DOC-CITED redteam/cotrain.go:20-52].

4. The brain’s explanation is quoted exactly, never rewritten by an agent. The verdict carries verbatim trace fields — SelectedAction, Result, SelectionReason, ExclusionKind, SLOGateResult, NoopReason [DOC-CITED coverage.go:1700-1718].

9. Consensus & deliberation (WS-4)

Consensus here is the mechanism by which each team finds better solutions faster. Within a team the agents propose, critique, merge and rank candidates, and agree on which to send to the brain first; they learn from the brain’s decline reasons each round and converge on the next best candidate. Agreement decides *what to test and in what order* — it never approves. Only the brain and the measured gates approve.

9.1 The in-team deliberation protocol

Each team (the attack team; the actuator team) runs the same protocol independently, per round, on cheap predicted scores — no brain or twin call happens inside deliberation, so it is fast.

• Roles. *Proposers* — the diverse persona specialists (§5/§7) emit candidate fragments/actuators. *Critics* — peer personas adversarially read each candidate and predict which deterministic check will reject it (attack side: which of C1–C6 is weakest? actuator side: will the brain fail to SELECT, or a gate fail?). *Aggregator* — deterministic code that merges, scores and ranks; it is not an agent and casts no opinion.

• Rounds of critique. A bounded number of critique rounds (a configurable parameter, §14). Each round: every candidate collects peer critiques, candidates are merged (dedup by fingerprint; complementary fragments fused into cascades), and each gets a predicted-pass score from a deterministic rank-aggregation of its critiques (e.g. Borda/median rank), never a free-form vote.

• How disagreement is resolved. Disagreement over *ordering* is resolved by the deterministic rank-aggregation, and the spread is recorded (stated, not averaged into a false consensus). Disagreement over *inclusion* is resolved in favour of evidence: a candidate that carries a specific cited precondition/edge is never dropped by a vote — see §9.2.

• How ranking is agreed. The agreed order is the deterministic aggregate of the diverse personas’ predicted-pass scores — most-likely-to-pass first. Ties fall through to a fixed key (candidate fingerprint). The ranking is a *prior over what to test*, nothing more.

• When to stop deliberating. Stop at the earliest of: (a) a fixpoint — no new distinct candidate is produced; (b) a stable top-of-queue across two rounds; or (c) the critique-round budget. Then the ranked send-queue is handed to the gate+brain.

• Learning from decline reasons. When the brain/gate declines a tested candidate, its machine-readable reason (the closed ExclusionKind/Status vocabulary — no-cover, slo-gate, existential MissingKeys, a feasibility veto string, …) is fed back as the next round’s *decline memo*. The team then converges on the next best candidate that specifically avoids that decline (slo-gate → a gentler in-process actuator; MissingKeys → an actuator covering those keys; no-reachable-path → a different edge).

function Deliberate(team, signal, declineMemo, budget): # inside ONE team, per round; no brain/twin call

cands = concat(persona.Propose(signal, declineMemo) for persona in team.diverse_personas)

for r in 1..budget.critiqueRounds:

for c in cands: c.critiques += [p.Critique(c) for p in team.peers(c)] # predict the weakest check

cands = Merge(cands) # dedup by fingerprint; fuse complementary -> cascades

for c in cands: c.predScore = RankAggregate(c.critiques) # Borda/median, deterministic

if Fixpoint(cands) or TopStable(cands): break

queue = RankDesc(cands, by=predScore) # most-likely-to-pass FIRST (convergence speedup)

queue = KeepAlways(queue, EvidenceBearingMinority(cands)) # a cited-evidence minority is never voted out

return queue # ORDER + inclusion to TEST; approval is decided ONLY by brain + measured gates

In-team deliberation. It chooses what to test and in what order; it never approves. The orchestrator then runs the queue through the gate+brain (§9.3), early-stops on the first confirmation, and feeds the decline reason of any reject back as declineMemo for the next round.

9.2 Diversity decorrelates error; a minority with evidence is still tested

Majority agreement reduces random errors and hallucinations — but only to the extent agents’ errors are independent [PAPER-CITED WS-7: More Agents Is All You Need, TMLR 2024]. So the roster uses diverse personas AND a mix of underlying models, so their errors are less correlated and the agreed ranking is a better prior. Because agents can still share a blind spot, agreement is never proof: a minority proposal that carries specific evidence (a concrete cited precondition, edge, or cover key) is still sent to the brain — it is guaranteed a slot in the send-queue and is never eliminated by the vote. The correct answer is a minority view in roughly 1-in-4 divergent cases [PAPER-CITED WS-7: minority-truth, Nov 2025], so suppressing dissent would suppress truth. Ranking only reorders; the brain and the measured gates decide.

9.3 How it speeds convergence

• Test the most promising first. Ranking by predicted-pass means the first brain/twin evaluation is the one most likely to confirm — fewer expensive evaluations to the first WIN.

• Guided, not blind, search. Decline-reason feedback turns each round into a directed step (avoid *this* exclusion), collapsing the candidate space geometrically instead of linearly — the same reason the loop re-attacks winners with memory (§3).

• No wasted evaluations. Merge removes duplicate/again-equivalent candidates before they cost a brain call; the fixpoint/top-stable stop avoids over-deliberating.

• A better prior from decorrelated agents. Diverse models make the agreed order a sharper prior, so the ranking’s top-k contains the eventual winner more often — verification stays a first-class, separate component, per MAST [PAPER-CITED WS-7].

Ground truth. 11. The per-customer RL record (WS-6)

Every proven (attack, actuator, brain-verdict) triple from the competition — with the brain’s explanation quoted exactly and the seven metrics attached — is appended to the per-customer RL learning record, shadow only. 11.1 The governed data path

1. Measured observation, not a label guess: a triple is admitted only after the actuator’s effect is externally, exactly confirmed on the twin — the RLS recursion is fed only after a rotation’s replacement reaches PodReady; failed observations create no loss evidence; admitted records are immutable, sha256-named, re-validated on read [DOC-CITED cost/rls.go:16-17; lossobserver/observer.go:40-41; losshistory/store.go:1-2].

12. External SOTA — what the literature says (WS-7)

The design’s central choices — agents generate, a deterministic oracle judges, and an adversarial competition hardens the defence — are strongly supported.

• Rejecting LLM-majority voting is justified. *More Agents Is All You Need* (TMLR 10/2024): voting helps only when agent errors are independent; LLMs share corpora so errors correlate, and the correct answer is a minority view in ~1 in 4 divergent cases (arXiv 2511.07784, Nov 2025). LLM-as-judge is biased — position bias (ACL/IJCNLP 2025), self-preference up to +73pp. [PAPER-CITED] → use agents for generation breadth, never adjudication.

• Ground truth = observed execution effect; and score the defender against what the attacker verifiably did. Dreadnode ‘Catch Me If You Can’ (Black Hat 2026) auto-derives the blue rubric from what red demonstrably executed — the same principle as our round-by-round re-attack and G1 effect-confirmed. MITRE CALDERA/BAS judge by observed effect. PentestJudge (Aug 2025) reaches only F1≈0.83 as an LLM judge. [PAPER-CITED]/[VENDOR-CLAIM]

• Adversarial self-play / iterated attack-defence is the established way to harden a defence (red/blue co-training; our redteam PPO/POMDP/QD already does this against the real DualSolver) — the competition is not novel risk, it is the known-good pattern. [PAPER-CITED]

• MulVAL-style logical attack graphs (USENIX 2005; ATT&CK-coverage survey 2022) — an actuator passes iff it provably cuts a reachable path; replayable and diff-able, exactly our recon Fact.Key() + three reachability edge kinds. [PAPER-CITED]

• Shallow functional hierarchy; verification/termination as a first-class component (MAST, UC Berkeley 2025); strong single-agent baseline first; MCP for typed tool access, A2A for delegation. [PAPER-CITED]/[VENDOR-CLAIM]

17. STEELMAN — the cheaper alternative, and where it fails

The alternative: skip the agent swarm and the competition. Ship a fixed, scripted red/blue battery — curated known attacks (CALDERA/BAS atomic tests) replayed against each customer, the brain scoring the actuators. No LLM generation, no rounds, far cheaper, fully deterministic. For the attacks it contains, it is as rigorous as the loop — same brain, same twin, same probe. WS-7 confirms outcome-grounded scripted scoring is the *reliable* part of the field.

Where it fails to generalize per-customer — and why the competition wins anyway:

• It cannot re-attack its own winner. The whole point of your directive is that after a defence wins, the attacker searches for a new real path *around it*. A fixed battery has no mechanism to adapt to the defence it just provoked — it replays the same scripts. The competition hardens the defence against exactly the adversary a static battery cannot represent. [§3]

• It cannot synthesise the attack only this cluster’s topology admits. The gate is driven by *this customer’s* RBAC, NetworkPolicies, co-residency, models, EPSS digests; the battery under-covers the customer-specific long tail. [§6]

• It cannot size itself — same N scripts for a 3-pod and a 2,000-pod fleet; the loop derives tens→low-hundreds of seats from the scan. [§4]

• It cannot discover the cheaper, lower-dwell actuator — the battery pairs each attack with a pre-chosen defence; the competition proposes any cover-granting actuator and ranks by measured dwell/cost, and the RL record remembers what beat this customer’s adversary. [§8, §11]

Verdict. Keep the battery — as the competition’s *regression suite* and the strong single-agent baseline MAST demands — not its replacement. It is the subset of the loop’s output that is pre-pinned; the competition is what generalizes and hardens per-customer, and both share the same deterministic referee.

• The output is an architecture (design), not product code. ✓

• The adversarial competition is explicit and central: attacker re-attacks the winners each round until STABLE or CANNOT-HELP, with a round-by-round record (§3). ✓

18.1 One-line founder recommendation

Build the verification loop as an adversarial competition — attack and actuator agents play rounds on a read-only twin, the deterministic brain + reachability/feasibility/SLO checks are the sole judge, the attacker must beat each winning defence or the loop declares STABLE/CANNOT-HELP, and every proven triple with its seven measured metrics is stored shadow-only for human-approved calibration — because it is the only design that hardens a per-customer defence against an adaptive adversary without ever weakening Phorvex’s ‘no LLM in the belief path’ guarantee or touching the brain.

Appendix B — Rev 5 change set

Phorvex Verification Loop — Rev 5 change set (library-first)

Rev 5 keeps every Rev 4 component. It changes one thing: the loop no longer invents attacks. It builds a reviewed attack-coverage library first (WS-8), then scans a stack, selects the library entries that apply, and runs the existing Rev 4 competition on them. This removes the part that was failing (agents authoring attacks) and keeps the valuable part (the deterministic brain developing and proving the right actuator).

Apply these edits to Phorvex-Verification-Loop-Architecture-Rev4.docx to make it Rev 5, and to the WS files.

Change log line (top of the doc)

Rev 5 makes the pipeline library-first: a reviewed attack-coverage library (WS-8), built from MITRE ATLAS 2026.09, MITRE ATT&CK (Containers/Cloud/Linux), OWASP LLM/Agentic/MCP, the Microsoft Threat Matrix for Kubernetes, CIS/NSA-CISA (preconditions) and NIST AI 100-2/AVID, is Stage 0. The generator (WS-2) becomes a select-and-fit step over that library, not an attack author. Coverage buckets, the coverage matrix, and a control-surface limit on actuator design are added.

New §0.5 — The two-stage pipeline (insert before §1)

STAGE 0  BUILD LIBRARY (offline, reviewed; WS-8)
   load ATLAS/ATT&CK/OWASP/MS-matrix/NIST  ->  one entry per in-scope technique
   each entry: id, preconditions[], attacker_end_state, expected_actuator,
               confirmation_probe, coverage_bucket, control_surface
   bucket-4 entries kept WITH their reason (the honest coverage edge)
        │  humans/partners review entries; agents do NOT author attack content
        ▼
STAGE 1  SCAN & SELECT (plug-and-play; WS-1 scan + new select step)
   scan the stack  ->  facts (pods, images+EPSS, identity, routes, GPU/serving, agents/MCP)
   an entry APPLIES when its preconditions[] hold on this stack
   selection agents bind applying entries to real workloads + customise params to the stack
        ▼
LOOP     COMPETITION (unchanged, Rev 4 §3)
   per applied entry: DevOps stands up the END-STATE FIXTURE on the twin
   -> deterministic gate confirms the end state is present (C1..C6)
   -> validator proposes actuator -> brain decides -> G1 proves the state is GONE
   -> re-attack winners -> STABLE or CANNOT-HELP
   CANNOT-HELP (bucket-3) -> design roster synthesises an actuator (Rev 4 §3.4),
                             limited to the control surfaces below

§2 rails — add two invariants

Rail 9 — Agents never author attack content. Generator agents may only select library entries and fit their parameters to the scanned stack. New library entries are authored and reviewed by humans (or a contracted testing partner) and bound to public framework IDs. [enforced procedurally; the gate still admits nothing to REAL without C1..C6]

Rail 10 — Actuator design is surface-bounded. The design roster (§3.4) may propose actuators only on surfaces Phorvex can act on: k8s-api, cni/dataplane, node, serving-stack, identity/keys, artifact-registry, agent-runtime. Anything outside is a product decision, not an agent output.

§3.4 — design roster trigger (reword)

Trigger is now: a bucket-3 library entry reaches CANNOT-HELP (confirmed-applicable, infra-reachable end state, no enabled actuator passes). Bucket-4 entries never trigger design — they are the honest edge.

§4 scan — add the end-state fixture contract

After the scan yields facts, each applied entry gets an end-state fixture on the twin: the minimal representation of the attacker-held state the actuator must remove (e.g. a marker process for a foothold, a poisoned-adapter label for a loaded bad adapter, a minted stale token for a credential, a planted index doc for RAG poisoning). The fixture represents the result, never the exploit. This is DevOps/AI-engineer fixture work and needs no offensive capability.

§8 — add the coverage-matrix output

The loop emits, per source framework, every technique tagged covered | after-effect | design-stage | out-of-scope(reason), generated from phorvex-attack-library.csv. It is both an engineering artifact and a sales artifact, and it matches the datasheet’s “What it will not do”.

§14 — new configurable parameters

library.sources[] (which frameworks + versions), library.refreshCadence, select.preconditionStrictness, fixture.timeoutPerEntry. Fixed invariants: rails 9 and 10; bucket-4 never triggers design; agents never set an entry’s bucket to a lower number without human approval.

Appendix C — Generator Rev 5 (WS-2)

WS-2 (Rev 5) — Generator = library select-and-fit (replaces “attack author”)

0. The invariant this serves

The generator produces nothing new about how to attack. It selects reviewed entries from the WS-8 library and fits their parameters to the scanned stack. Every REAL promotion still requires the deterministic C1–C6 gate; agent agreement is never evidence. (Rev 4 §6 gate is unchanged.)

1. What changed from Rev 4 WS-2

Rev 4 | Rev 5

Persona agents emit hypothesised attack fragments | Persona agents select applicable library entries and bind them to real workloads

Novelty came from the agents | Novelty comes only from new human/partner-reviewed library entries

Fragment schema invented per run | Fragment = a library entry instance: {entry_id, bound_workload, fitted_params, preconditions_checked}

2. Select-and-fit algorithm

for entry in library.where(bucket in {1,2,3}):
    if entry.preconditions ⊆ scan.facts(workload):      # entry APPLIES
        inst = bind(entry, workload)                     # pick pod/ns/identity/route from the scan
        inst.fitted_params = fit(entry, workload)        # e.g. which adapter label, which SA, which route
        emit HYPOTHESIZED inst                            # still must pass C1..C6 to become REAL

Fitting is parameter substitution from scan facts only (names, labels, digests, routes). It never adds a step the library entry did not already contain.

3. Roster (unchanged shape, new job)

T0 orchestrator owns the scan snapshot + the applied-entry queue. T1 are per-tactic selectors (they know which library entries live under each ATLAS/ATT&CK tactic). T2 are per-domain fitters (k8s / ai-serving / agentic-MCP) that bind parameters. T3 chains applied entries into multi-stage instances over confirmed edges (respecting the library’s own leads-to where present). No tier authors attack content.

4. The gate is unchanged

C1 reachability · C2 RBAC · C3 precondition facts · C4 CVE/EPSS · C5 kill-chain evidence · C6 source trust. A fitted library instance is REAL only when every precondition it carries is confirmed against scanned facts. Scanned text stays UNTRUSTED data (Rev 4 §6.1).

5. Growing the library (the only source of new coverage)

A new entry is added by a human or a contracted testing partner, keyed to a public framework ID, with: preconditions, attacker_end_state, confirmation_probe, bucket, surface. It enters the same way as the seed entries and is then selectable. Agents may propose a gap (“no entry covers ATLAS AML.Txxxx on this stack”) as text for human review; they do not write the entry.
