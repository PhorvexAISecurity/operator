# Protected serving-effect receipts

KV reset, distributed KV invalidate/migrate, and guardrail rotation retain their dispatch state in operator-namespace ConfigMaps. A slot is keyed by the exact target Pod UID and effect domain. KV reset and migrate share `kv-session-v1`; guardrail rotation uses `guardrail-variant-v1`. A pending or unknown slot blocks every policy and action that overlaps that domain.

Only the process that receives the successful resource-version update from `prepared` to `dispatching` sends the serving request. A `202`, timeout, cancellation, connection loss after dispatch, journal acknowledgement loss, or observed `dispatching` phase stays unresolved. Restart recovery does not repeat the request. Confirmed synchronous `200`/`204` effects may retry only the owned Pod metadata patch. Guardrail restoration is an explicit rollback against the exact receipt reference; metadata failure never triggers an automatic compensating request.

The controller limits each encoded receipt to 32 KiB and each selected epoch value to 4 KiB. Before creating a new target/domain slot it requires a complete uncached inventory below 1,000 protected serving records and 16 MiB of encoded records. This is bounded admission backpressure, not a strict global quota: concurrent distinct creates can temporarily overshoot the observed threshold. Terminal operations reuse their existing slot. Recovery deletes a valid terminal record only after an authoritative read proves the exact old Pod UID absent, using the receipt UID and resource version as delete preconditions. Unknown obligations, unreadable targets, and receipts changed by another owner are retained.

The production remote KV connector remains unavailable. For declared peers the default records one `not-sent-unimplemented` outcome per normalized peer and performs no remote request. After confirmed local invalidation it writes only `phorvex.ai/kv-local-effect-epoch`; it does not write the full migrate/session epoch or refresh full-session exposure. A connector supplied later must return an exact bounded outcome for every declared peer.

An unresolved receipt requires external investigation of the backend and Kubernetes audit trail. Do not delete or overwrite it while dispatch or recovery work can still be running. This release intentionally provides no automatic resolution for a possible-send result because the serving APIs do not expose a trustworthy asynchronous operation-status identity. Its synchronous-response fixtures model a backend contract in which `200`/`204` confirms the requested effect; they do not establish that every vLLM version satisfies that contract. In particular, deployed reset endpoints must separately prove their action-specific response body and semantics before mitigation credit. Real backend compatibility, credentials, workload availability, and distributed/hardware behavior remain live validation work.
