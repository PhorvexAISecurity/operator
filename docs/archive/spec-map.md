# Phoenix AMTD — Specification-to-Implementation Map

This report maps the security claims made across **4 academic papers** (PHOENIX: Adaptive Containers; Adaptive Security for AI Infrastructure with AMTD; ADA: Automated Moving Target Defense for AI Workloads; Proactive Security for Large-Scale AI Inference / Adaptive Container Orchestration at the Edge) and **2 product pages** (Phoenix for AI; Phoenix for Kubernetes) onto the **5 source repositories** that constitute the Phoenix AMTD implementation (`phoenix-main`, `time-based-trigger`, `prometheus-integrator`, `kubearmor-integrator`, `falco-integrator`). For each of 6 mechanisms, claims were extracted with exact section/page citations, mapped to exact files/symbols/line ranges, and adversarially verified by independently re-opening both the code and (where available) the cited documents. **Headline finding:** only the *time-based trigger* and a *minimal pod-delete-and-reschedule restart* are genuinely implemented; the distinctive, marketable mechanisms — **node rotation, randomized/jittered intervals, telemetry-weighted adaptation, signed-baseline drift correction, golden-image/warm-pool swap, and NVIDIA-NIM AI-inference rotation** — are claimed by the documents but absent from code (the on-disk `NIM` is "Node Infrastructure Module," not NVIDIA Inference Microservice). Every quantitative result (e.g., Persistence <4%, dwell <60 min, 94% disruption, 99.8% availability, `MODEL_ROTATION 3.2s`) is a paper/marketing/dashboard value with no measurement or enforcement code.

## Mechanism details

### Container / node rotation

**What the papers/products claim**

- Containers rotate, terminate, and re-initialize continuously ("Containers Rotate Constantly"), eliminating the foothold; suspect workloads are terminated and replaced; blocks persistence/lateral movement. Mechanism stays at the *container* level (does not describe rotating NODES) (PHOENIX: Adaptive Containers, §IV "Implementation of Randomization" / "Automated Reset on Threats" / "Strategic Alignment", pp.2-3).
- Rotating containerized inference workloads via immutable signed golden images, Leader-Worker Sets (one active leader + N-1 warm shadow workers), a Rotation Controller that "Triggers restart or replacement on schedule (+ jitter)," with leader swapped for a warm worker and inference parameters (API key, endpoint path) rotated; restarts wipe in-memory footholds. Container/identity rotation, not node rotation. Results: Persistence Success Rate 95%+ → <4%; Dwell Time 150+ days → <60 mins (Adaptive Security for AI Infrastructure, §3 AMTD Architecture / §3.1-3.2, p.2; Contrast table, p.4; Performance Metrics table, p.5).
- Automated continuous "destroy and respawn" of Kubernetes PODS via rolling update orchestrated by an "ADA Controller"; pod-level only (node/host compromise deferred to future confidential-computing work §6.3.4). Qualitative only: "Increase the cost of persistence of the attacker significantly"; Table 1 "Ephemeral pod lifecycle disrupts attacker persistence" (ADA, §1 pp.1-2; §3.1 p.5; §3.2-3.3 pp.5-7; Fig.1 p.6; Table 1 Pod Escalation p.13).
- A Kubernetes Operator + Rotation Engine re-deploys workloads with "new container IDs, ephemeral node assignments, and shuffled port mappings"; defensive intent framed as "rotating containers, nodes, and configurations." Quantitative: Persistence 5%, PrivEsc 3%, Lateral 4%, Impact 2%; abstract claims up to 94% disruption, dwell reduced to minutes, availability 99.8%, cost 1.3-1.7% (Proactive Security / Adaptive Container Orchestration, §IV.B Rotation Engine & §IV.D Rotation Workflow p.3; §III.D p.2; §V.D p.4; Tables I & II p.5; Abstract p.1).
- "Phoenix rotates the specific pods handling AI requests"; "panic mutation — moving the model to a clean, isolated node"; "Endpoints rotate, model access paths change." Claims "Broken session persistence for AI attackers"; hero widget `MODEL_ROTATION: 3.2s`, `PIPELINE_INTEGRITY: 99.97%` (Phoenix for AI, "Three Technical Pillars" — Pillar 01 & Pillar 03, pp.3-4; hero "Inference Telemetry" widget, p.1).
- Kubernetes Operator that "continuously mutates your cluster topology"; "Continuous Pod Mutation" replaces pods "with randomized UUIDs and internal IPs"; "terminates and recreates them ... Attacker persistence is severed on every cycle"; "Panic Mutation" triggers immediate workload rotation. **No node rotation described — pods/workloads only.** Telemetry-style figures `PODS_ROTATED 1,253`, `MUTATION_CYCLE 1.8s`, `DWELL_TIME 0ms` (Phoenix for Kubernetes, hero "CLUSTER TELEMETRY" panel p.1; "Continuous Pod Mutation" & "Panic Mutation" p.3; pillar 01 p.4).

No Golden Image Repository, no immutable/signed pull, no Leader-Worker-Set, no warm/shadow-worker swap. Identity-shuffling claims (randomized UUIDs/IPs, shuffled ports, rotated API key/endpoint, updated Service Endpoints) have **no supporting code** — pod IP changes only incidentally on recreation. All quantitative figures are dashboard/marketing values with no measurement code.

### Randomized intervals

**What the papers/products claim**

- Core thesis: containers rotate "constantly" as "high-frequency randomization," invoking von Neumann's minimax; randomizes the system STATE/target rather than explicitly jittered TIME intervals (timing described as "constant"/"continuous"/"high-frequency"). Theoretical claim: a perfectly unpredictable mixed strategy "guarantees the best possible worst-case outcome ... reducing the attacker's expected payoff to ... zero" (PHOENIX: Adaptive Containers, §III "Von Neumann's Minimax" & §IV "Containers Rotate Constantly", p.2).
- Rotation on a schedule WITH JITTER: "Rotation Controller: Triggers restart or replacement on schedule (+ jitter)"; "Default Rotation Interval R = 60 minutes ± jitter (10-30%)"; "Randomized endpoint URLs with hash-based TTL." Quantified jitter 10-30% around 60 min; conceptual claim that higher entropy/smaller R minimizes expected ASR (Adaptive Security for AI Infrastructure, §3.1 & §3.2 p.2; Mathematical Model p.2; §5 Deployment p.6). **This doc explicitly claims jittered intervals.**
- Randomization of rotation PARAMETERS rather than jittered time: "randomized parameters: new container IDs, ephemeral node assignments, shuffled port mappings"; best config labeled "Adaptive / Randomized Rotation (Phoenix)" vs fixed "Timed Rotation (30 min)"; "Staggered rotation to avoid simultaneous restarts." Adaptive/Randomized yields lowest attack success (<10% all stages); cut exploitable surfaces >80% (Proactive Security, §IV.B p.3; Tables I & II & notes p.5; §V.A p.3; Fig.1 p.6).
- Randomization of pod identity/scheduling rather than explicitly jittered timing: pods replaced "at configurable or telemetry-driven intervals with randomized UUIDs and internal IPs"; bullets "Configurable rotation intervals" + "Randomized pod scheduling." No quantitative jitter range; `CLUSTER_ENTROPY` shown in telemetry widget (Phoenix for Kubernetes, hero + telemetry panel p.1; "Continuous Pod Mutation" p.3; pillar 01 p.4).

**Implementation in code**

- `phoenix-main` `api/v1beta1/adaptivemovingtargetdefense_types.go` — `AdaptiveMovingTargetDefenseSpec`, L29-41. Only `PodSelector` + `Strategy[]`; **no interval/period/schedule/rotation-frequency/jitter field.**
- `time-based-trigger` `internal/controller/pod_controller.go` — `TimeBasedTriggerScheduleAnnotation`, L50. The only timing-interval input in the whole product — an operator-supplied fixed cron or duration string.
- `time-based-trigger` `internal/controller/pod_controller.go` — `SchedulableDuration.Next`, L65-69. Wraps a fixed `time.Duration`; `Next(t)` = `t.Add(de.duration)` — a deterministic, constant offset.
- `time-based-trigger` `internal/controller/pod_controller.go` — schedule parse, L126-136. `cron.ParseStandard` or fallback `time.ParseDuration`; both fully deterministic.
- `time-based-trigger` `internal/controller/pod_controller.go` — `nextRun`/`RequeueAfter`, L150-180. `nextRun = sched.Next(lastRun)`; requeues with the plain time delta. The next rotation fires at a fixed, predictable time. **No jitter.**
- `phoenix-main` `internal/controller/adaptivemovingtargetdefense_controller.go` — Reconcile return, L196. `ctrl.Result{RequeueAfter: 10 * time.Second}` — hardcoded constant.
- `phoenix-main` `internal/controller/nim_controller.go` — `NIMPolicy.RequeueAfter` default `10*time.Second`, L46-68. Configurable-but-constant; no jitter.
- `kubearmor-integrator` `kubearmorlog/logClient.go` — `Feeder.DoHealthCheck` (`rand.Int31`), L82-94. The ONLY use of `math/rand` in any repo — a gRPC health-check nonce, unrelated to timing.
- `phoenix-main` `README.md` — marketing prose, L22-32. Claims "randomized or policy-defined intervals" / "Managed Randomness" / "Randomized Rotation" — **no backing code.**

*Searched but absent:* grep across all 5 repos for `rand`/`Intn`/`Int31n`/`jitter`/`Jitter`/`wait.Jitter`/`shuffle`/`Float64`/`Ticker` → 0 matches relevant to interval timing (only the `rand.Int31()` health-check nonce; `sigs.k8s.io/randfill` appears only as an indirect test dependency). No jitter/percentage-range (`10-30%`, `±`, `hash-based TTL`) logic. The AMTD CRD and the `time-based-trigger` pods CRD have no interval/period/schedule/jitter field; timing comes solely from a free-form pod annotation. `prometheus-integrator` and `falco-integrator` contain no `RequeueAfter`/`Ticker`/schedule logic at all.

**Verdict — `claim-without-code`.** What the papers describe (jittered timing, "R = 60 min ± jitter 10-30%," "high-frequency randomization" of timing, "hash-based TTL randomized URLs," a probabilistic mixed-strategy clock) is absent. The only scheduling implementation (`time-based-trigger/internal/controller/pod_controller.go`) is fully DETERMINISTIC: a fixed cron pattern or constant duration, with `Next(t) = t.Add(duration)` and `RequeueAfter = nextRun.Sub(now)`. Phoenix's own controllers use hardcoded constants (AMTD `10s`; NIM `10s`/grace `30s`; SecurityEvent `2s`). The single `math/rand` call in the entire codebase is a gRPC nonce, not a timing source. The README's "randomized intervals" / "Managed Randomness" wording is unsubstantiated marketing.

### Telemetry-driven adaptation

**What the papers/products claim**

- Weakly/implicitly: "Automated Reset on Threats" where "Suspect workloads are immediately terminated and replaced," implying detection triggers a reset; no telemetry/metrics pipeline described. Claims the reset is a "perfect counter-action, resetting the game state" (PHOENIX: Adaptive Containers, §IV "Automated Reset on Threats" bullet, p.3).
- Telemetry/metric-driven (anomaly-triggered) rotation: Prometheus scraping NIM metrics, AlertManager signaling the Phoenix Operator to "#4: Kill"; "Restart triggers from Prometheus metrics (e.g., anomaly rate)"; "Anomaly detection hooks can trigger custom kill/redeploy logic via CRDs." With anomaly-based rotation, recovery is "preemptive" and MTTR <5 minutes (Adaptive Security for AI Infrastructure, architecture diagram p.3; §5 Deployment p.6; §5.2 diagram p.7; "Why It's Harder to Attack AMTD" p.5).
- Optional/extended "Adaptive Mutator Layer": CRD-defined mutation policies triggered by Kube-state-metrics, Prometheus alerts, and OPA Gatekeeper violations; Listing 1 `ContextMutationPolicy` with `triggers.telemetrySources`; Fig.1 shows Telemetry Feeds + RL Agent → Policy Engine; future work proposes ML-based anomaly detection / behavioral scoring. Qualitative only (ADA, §2.6 & §2.6.1 + Listing 1 pp.3-4; §3.1 p.5; Fig.1 p.6; §5.6.2 pp.11-12; §6.3.3 p.14).
- Central pillar: "Telemetry-Driven Adaptation: Rotation schedules and configuration mutations are triggered by runtime metrics (e.g., Prometheus alerts) rather than fixed timers"; "Telemetry-Weighted Rotation Scheduling: Rotation frequency is ... proportional to anomaly scores ... (GPU entropy, query deviation, cache misses)." Claims accelerating rotations during suspicious activity reduces stealth advantage (Proactive Security, §II.D.2 p.2; §IV.C.3 p.3; §IV.B p.3; §IV.A p.2).
- "Context-Aware AMTD": "Defense adapts based on inference load, model type, and threat telemetry"; "Agentic Defense Logic" agent observes model I/O and triggers immediate mutation on a malicious payload; GPU pillar monitors utilization. Qualitative; `PIPELINE_INTEGRITY 99.97%` illustrative (Phoenix for AI, "Context-Aware Defense" panel p.3; Pillar 03 & Pillar 02 p.4; "Inference Telemetry" widget p.1).
- Signal-driven adaptation: "Panic Mutation" — "Falco detects suspicious activity, Phoenix triggers immediate workload rotation"; "Event-Driven Defense" — "Falco and eBPF signals trigger panic mutation." Qualitative; rotation is "immediate" (Phoenix for Kubernetes, "Continuous Pod Mutation" p.3; "Panic Mutation" p.3; "Event-Driven Defense" card p.4).

**Implementation in code**

HTTP webhook receiver for Alertmanager; for each firing alert creates a `SecurityEvent`. Does NO metric scraping, NO PromQL, NO anomaly scoring: `Rule.Type=alert.Labels["type"]`, `Rule.ThreatLevel=alert.Labels["threatlevel"]` copied verbatim (L141-142). The anomaly decision happened entirely upstream (not in any repo). **Telemetry INGEST, not adaptation.**
- `prometheus-integrator` `cmd/main.go` — `PrometheusResponse`/`Alert` structs, L55-76. Data model for the inbound Alertmanager webhook; a pre-computed alert envelope (no `nim_requests_running`/`nim_request_latency`/`gpu` fields).
- `falco-integrator` `cmd/main.go` — `FalcoBackend.FalcoHandler`, CRD field `SecurityEvent.Spec.Rule`, L78-127. Maps one Falco event → one SecurityEvent (`Rule.Type=response.Rule`, `ThreatLevel=response.Priority`, `Source="FalcoIntegrator"`, L111-115). Stateless 1:1 pass-through; backs the "Falco-triggered rotation" claim. No eBPF code, no scoring, no feedback.
- `kubearmor-integrator` `cmd/main.go` — `kubeArmorEventHandling`, CRD field `SecurityEvent.Spec.Rule`, L51-97. Consumes KubeArmor policy-violation events from a gRPC channel and emits one SecurityEvent each (`Type=PolicyName`, `ThreatLevel=Severity`). Stateless relay; never aggregates/counts/scores over time.
- `kubearmor-integrator` `kubearmorlog/log.go` — `StartObserver`, L18-56. Package doc "connects and observes telemetry from KubeArmor" — the only use of the word "telemetry" in Go code. Pure transport, no analysis.
- `phoenix-main` `internal/controller/securityevent_controller.go` — `SecurityEventReconciler.Reconcile` (decision core), CRD field `AdaptiveMovingTargetDefense.Spec.Strategy[].Rule -> Action`, L137-149. Selects action via `reflect.DeepEqual(strategy.Rule, securityEvent.Spec.Rule)` (L139) — exact static equality of {Type,ThreatLevel,Source}. **NO feedback, NO learning, NO evolving state: identical telemetry always yields the identical action.**
- `phoenix-main` `internal/controller/securityevent_controller.go` — action execution, L197-372. Executes the matched action (Delete/Debugger/CustomAction/Quarantine) — a one-shot deterministic effect, with no telemetry-derived parameters.
- `phoenix-main` `api/v1beta1/adaptivemovingtargetdefense_types.go` — `Rule`/`ResponseStrategy`, CRD field `Strategy[].Rule{Type,ThreatLevel,Source}`, L258-281. A `Rule` is three plain strings matched literally; **NO anomaly score, threshold, metric source, telemetry weight, or rotation-cadence field.** (`Status` struct empty, L284-287.)
- `phoenix-main` `api/v1beta1/securityevent_types.go` — `SecurityEventSpec`, L27-42. Carries only Targets, Rule (3 strings), Description — **no metric value/score/magnitude.**
- `phoenix-main` `internal/controller/nim_controller.go` — `NIMReconciler.Reconcile` / `DefaultNIMPolicy`, L45-133. Reschedules pods on a fixed `RequeueAfter` (default 10s, L56; returned L132) only when a timed/`TimeBasedTrigger` rule is present (`FindTimedEvent`, L121/136-143). Never computed from latency/throughput/GPU.
- `time-based-trigger` `internal/controller/pod_controller.go` — `PodReconciler.Reconcile`, L115-180. *Searched but absent:* across all 5 repos, ZERO functional matches for `anomaly`, `entropy`, `risk-score`, `weighted`, `telemetry-weighted`, `adaptive`, `learn`, `feedback`, `scoring`, `behavioral`, `RL`/`reinforce`, `proportional`, `accelerate`, `threshold`, `histogram`, `cache-miss`. `promql`/`query_range`/`client_golang`/scrape → 0; "prometheus" appears only as import paths + webhook struct names; "metric" only as controller-runtime's own `/metrics` self-exposition (`phoenix-main/cmd/main.go:57-76`). Named metrics (`nim_requests_running`, `nim_request_latency`, `gpu`, `utilization`, `latency`, `throughput`) → 0. ADA specifics (`ContextMutationPolicy`, `telemetrySources`, `ResourceAdjustment`, `EnvPatch`, `ContainerImageUpdate`, `opa`, `gatekeeper`, `ebpf`) → 0. Every located `RequeueAfter` is a constant or static annotation. `AdaptiveMovingTargetDefenseStatus` is an empty struct (L284-287) — no observed-state/feedback channel.

**Verdict — `partial`, shallow ingest layer only.** A telemetry intake plane exists: three integrators (prometheus, falco, kubearmor) receive runtime signals and translate them into `SecurityEvent` CRs, and the operator reacts immediately. This substantiates the weaker literal claims ("Falco detects suspicious activity → immediate rotation"; "telemetry rebinding triggers alerts and re-spawns services"; the Alertmanager→Phoenix "#4: Kill" path). **Missing vs the claims:** (1) NO metric pipeline in code — `prometheus-integrator` is a passive Alertmanager WEBHOOK SINK, never a Prometheus client; the "anomaly rate"/"high_gpu_usage"/threshold logic lives in external rule files in NONE of the 5 repos. (2) Response is STATIC rule→action matching (`securityevent_controller.go:139` `reflect.DeepEqual`) — no feedback loop, RL agent, behavioral/risk scoring, or ML anomaly detection. (3) NO telemetry-weighted rotation — every cadence is a hard-coded constant or static cron/duration; no `RequeueAfter` is computed from any metric. (4) The CRD cannot express adaptation — a computed anomaly score has nowhere to live and would be ignored by the matcher. (5) NONE of ADA's "Adaptive Mutator Layer" specifics exist. Net: telemetry INGEST is wired end-to-end; telemetry-driven ADAPTATION is not implemented.

### Drift correction

**What the papers/products claim**

- Correction as forcibly restoring workloads from an immutable known-good baseline: "Golden Image Repository: Immutable, signed copies of containerized workloads"; "LWS Golden Pools"; containers "forcibly restarted from golden state" and "pulled from known-good sources"; platform "self-healing." Baseline-restoration/anti-tamper, not an explicitly named "drift detection" loop. Supply-chain attacks "mitigated with signed, verifiable images and immutable baselines"; Persistence Success Rate <4% (Adaptive Security for AI Infrastructure, §3.1 p.2; "Why It's Harder to Attack AMTD" p.5; Contrast table p.4; §5.1 p.6).
- Side-benefit of replace-not-patch: "Replacing instances rather than patching them reduces configuration drift and eliminates persistent threats"; instances "continuously refreshed to maintain a secure baseline"; ephemeral-infra mitigation adds "trigger resets on anomalies." No diff-against-baseline detector specified. Qualitative only (ADA, §2.5 p.3; §3 intro p.5; §5.3.3 p.12).
- Immutable Image Registry that "Stores trusted, signed AI inference container images" and "Ensures rollback capability to last known-good configuration"; each rotation deploys fresh from this registry; Confidential Deployment Mutations reset Seccomp/AppArmor/RBAC on rotation. Restoration of a known-good baseline, not continuous detect-and-reconcile (Proactive Security, §IV.B p.3; §IV.D step 1 p.3; §IV.C.4 p.3).
- Two framings: PROBLEM — "Config Drift" card ("Static configurations accumulate vulnerabilities"); SOLUTION — "Self-Healing Regeneration: Compromised workloads are automatically replaced with known-good baselines. No manual incident response" (GitOps-style, "GitOps Ready" card cites ArgoCD/Flux). Qualitative (Phoenix for Kubernetes, "Config Drift" card p.2; "Self-Healing Regeneration" p.3; "GitOps Ready" card p.4).
